## Overview

`@opencode-ai/auto` is the general CLI shell (bin `opencode-auto`): the init/amend/close/land/fork/remove-fork/fix/sync/release/reset/status/models/install-prompts/driver-helper subcommands and argument parsing are concentrated in `src/index.ts` (`--help`/`-h` prints the full usage with exit 0 and `<command> --help` one command's row — both render from the `COMMANDS`/`OPTION_HELP` table there, the one source of the usage text; an unknown command is a one-line refusal naming the closest live commands, and only a missing subcommand prints the full usage — stderr, exit 1) (the push commands retired — plans/0283: `run`/`plan`/`transfer`/`clarify` and the hidden `_lane` lane worker are permanent tombstones, each answering its one-line notice with exit 1 ahead of every flag, directory and lock semantics, and a retired name never suggests; the protocol does nothing via push — a phase's work is grants external coding agents claim over the executor protocol, the person's acts the daemon's operations, `opencode-auto-server serve` registering the project; the `continue` subcommand is retired — its notice names the daemon's transfer operation; `--continue` on any command errors with guidance; the `check` subcommand is retired — its notice names `fix --dryrun`; `models` prints the model registry's effective table from the core's `describeModels`/`checkModels`/`probeModels`, see the README's registry section), and all mechanisms are implemented in the core library `@opencode-ai/auto-core` (workspace dependency, subpath imports, driving opencode through its v2 SDK interface for per-task automated execution). Comments and user-facing messages are written in English, using the terms in [../auto-core/docs/glossary.md](../auto-core/docs/glossary.md).

## Commands (run inside this package directory)

- `bun run dev -- <args>` — run the CLI directly from source.
- `bun run build [--target <platform>]` — produce the standalone executable `dist/opencode-auto`.
- `bun typecheck` — `tsgo --noEmit`.
- `bun test` — runs `test/` (CLI parsing / e2e).

## Package boundary

- This package contains only the CLI shell (`src/index.ts`), build scripts, and e2e tests; core src, templates, and design documents live in `../auto-core`.
- **The core does not know shells**: never duplicate core logic here; when a need touches a core extension point, change `../auto-core` first (shell differences are injected via the `setShellProfile` profile or `registerTemplate`).

## Build conventions (developing this program)

- **Templates must keep the `with { type: "file" }` import** (via the `@opencode-ai/auto-core/templates/*` subpath) — the only way to embed them into the binary at compile time. New init copy templates → the `templates` mapping in `src/index.ts`; prompt/mode templates are changed in the `../auto-core` package.
- `src/templates.d.ts` provides path-string types for `*.md` / `*.json` imports; do not remove `resolveJsonModule: false` from `tsconfig.json`.

## Config semantics of init / amend / fix / reset (read before changing)

- `init` defaults to **stateless full overwrite**: `.opencode/auto/config.json` is decided solely by the parameters given this time, with absent keys falling back to `CONFIG_DEFAULTS` (the flagless hand-edited keys `acceptanceGate` / `build` are kept). The only watershed is `base = amend ? existing : { ...CONFIG_DEFAULTS, ...handEdited }` in `src/index.ts`; the `amend` command takes the existing config as the baseline. The two baselines load differently (plans/0052 D4): an amend carries every stored key over, so it loads strictly (`loadProjectConfig`); a full overwrite discards them, so `loadOverwriteBaseline` tolerates retired keys and `init` names each dropped one with its value. `init` writes the config layer only — never `docs/`; the rounds are the daemon's opening operations' (the transfer operation's, its plan operation in m mode; plans/0053 D31, re-homed by auto-core plans/0101 D2, re-keyed by plans/0283).
- `amend` (plans/0052 D25) is the amend baseline as a command of its own, sharing init's block (`amendCommand`): config flags only (`CONFIG_FLAGS`; `-p`, `-f` and `--amend` are usage errors), refused without config.json or without a key or brief revision, and it writes only what renders from the config (config.json, the contract, the AGENTS.md block) plus the project brief's manual revision (`--brief`/`--brief-file`, plans/0081 D11's channel — amend's alone) — never `opencode.json`, `.gitignore` or the rounds (init writes no brief at all: the stub model retired, the brief installed from the analysis's approved proposals). `init --amend` retired with P3c; the command is the only form.
- `fix` (plans/0052 D10/D11) takes no config flag and never resets a key: its rule table and boundary live in `../auto-core/src/config-fix.ts` (read its header before adding a rule). Hints that tell a person to change one key name `amend`; hints that tell them to refresh the contract or the AGENTS.md block, or to clear a retired key, name `fix` — never a flagless `init`, which resets every other key (DF8). A strict config failure appends `fixHint(dir)`.
- **Validate, then write** (plans/0052 D7): every refusal `init` can make — flag values, mode, the read-only prefix guard (`plannedPhaseUnits`; the phase-index reshape is the advance's — the transfer operation's committed re-derivation, plans/0206), prompt-library and intent-pack validation, and the commit-capability prerequisite (`commitIdentityProblem` in `../auto-core/src/git.ts`: inside a git work tree, git must be able to commit there, so a missing user.name/user.email refuses init; init only — the `amend` command touches an already-working project and is not covered) — happens before the overwrite guard and the first write. A new check goes there too, never after `saveProjectConfig`. Plain `init` also writes the wider `.gitignore` set via `ensureInitGitignore` (`../auto-core/src/gitignore.ts`: the driver workdir, local-only files and nested git repositories — the `.gitignore` itself and `opencode.json` are committed project surfaces, plans/0138, so a fresh clone receives the set); `reset`'s `removeGitignoreEntries` removes exactly that set.
- The phase-index prefix guard (completed phases in `docs/R-NN/phases.md` order must prefix the new value) judges the **effective value of this run** (`effectivePhases`), not "whether `--phases` was explicitly given" — otherwise a no-arg init would silently reset a staged project's phases to `"m"` and destroy the round layout. Any new path that affects `phases` must preserve this rule.
- The cleanup list and boundary rules of `reset` are documented in the header comment of `../auto-core/src/reset.ts` — read that entire comment before changing the list: only the config layer is cleaned, directories are always removed with `rmdir` (reclaimed only when empty, never `rm -r`), and the `opencode.json` shared with the main program is deleted only after a byte-for-byte comparison against the template.
- The push-command tombstones (plans/0283, `RETIREMENT_NOTICES` in `src/index.ts`): `run`/`plan`/`transfer`/`clarify` and the hidden `_lane` entry answer their one-line notices with exit 1, fired ahead of every other interception — a retired command has no flags, directory, help or lock semantics left to honor, and a retired name never suggests in the unknown-command refusal. The plan/transfer flag families keep their owned refusals on every live command through `OWNED_FLAGS`, re-keyed to the daemon surfaces: `--append`/`--force-close`/`--scaffold`/`--new-task`/`--export`/`--adopt`/`--round`/`--phase` name the task-add operation (`POST /projects/<project>/tasks`), the close-then-plan-operation pair, the intent pack's `## planning-input` section and the person's own document channels; `--resynthesize` names the transfer operation's request field; `-p`/`--file` (the strict ladder's close form and init's own) name the phase's `plan-input.md` read by the formulation. Run's session flags keep their retirement pointers on init (`pointers` in the init whitelist). The shell profile's `surface` seam renders the core's served teachings (the missing-index remedy, the driver-helper recovery rows) over the daemon surfaces.
- `close <ref> [dir] --reason <text> [--cascade] [--commit-changes | --stash-changes]` (plans/0053 D17–D22, D30) closes a unit without completing it (`closeUnit` in `../auto-core/src/close.ts`): the ref comes first (`positional[0]`, overriding the global directory rule; the shell validates the three canonical shapes — a subtask-shaped ref is a usage error naming them), only `CLOSE_FLAGS` are accepted (`--commit` gets the whole-name parsing notice naming `--commit-changes`/`--stash-changes`; config flags get the frozen-by-init refusal with the amend hint, `-p`/`--file` the plan retirement notice), and the order is argument checks → legacy-layout check → strict config load → `acquireRunLock(dir, "close")` → `closeUnit` → its `lines` printed (stdout when closed, stderr otherwise); exit 0 closed / 1 refused or usage / 2 commit or close-out failure. No confirmation prompt (the explicit ref and required reason are the confirmation); the undo is `git revert <sha>` of the close commit, printed in the output and valid before anything else runs — there is no `reopen`.
- `release [dir]` (auto-core plans/0103 D2/D3) is the release gate's shell row: flagless like `status` (the `FLAGLESS` list), refused on a legacy layout, no run-lock refusal (read-only — the clean-tree check inside `releaseCheck` makes a mid-flight certification refuse on its own), an invalid config only means the scan runs without the project's exemptions. The core's `releaseCheck` (`../auto-core/src/release.ts`) returns `nothing`/`problems`/`certified`; the row prints `✓ <destination> @ <HEAD>` lines on pass (exit 0), the `✗` findings with the fix-commit-re-run tail on exit 2, and `nothing to release` on exit 1. The containment findings the rounds record (close-out ⚠ lines, round-close warnings) are this gate's input ledger.
- The run lock (`../auto-core/src/lock.ts`, auto-core plans/0053 D3): `init`, `amend`, `fix`, `sync` and `reset` write what a running driver reads (the config layer, the materialized bundle files), so they refuse with exit 1 while `liveRunLock` finds another process holding `.auto/run.lock` — one check after the legacy-layout check, ahead of every command block; `-f` does not override it, and `fix`/`sync --dryrun` (read and print only) skip the refusal. The daemon-side operations (plan, transfer, clarify, reconcile, the coordinator) hold the lock in their own process; `close` and `land` take it around their writes; `status` never locks, and prints a live lock first. A new command that writes the config layer or the round setup joins that check.
- The destructive paths (`reset`, `fix` when it has fixable findings, and `init` overwriting an existing config) pass through the worktree-cleanliness gate (`../auto-core/src/clean.ts`) and the interactive confirmation (`confirm.ts`) before executing; `-f/--force` skips both; both checks must run before the first write to disk. `fix --dryrun` (plans/0052 D11: plan and print the findings, write nothing, exit 0 when there are none and 1 when there are any — the scripted gate that replaced the retired `check`) skips both by never writing; it keeps fix's other refusals (uninitialized, legacy layout).
