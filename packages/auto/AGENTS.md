Package-level notes for coding agents, kept lean: the core-mechanism documentation lives in the `../auto-core` package — file-level structure index in [../auto-core/docs/structure.md](../auto-core/docs/structure.md), the core/shell contract (boundary / dependency direction / merge flow) in [../auto-core/docs/shell-contract.md](../auto-core/docs/shell-contract.md), the retired target-directory behavior contract (historical, not maintained) in [../auto-core/plans/0029-behavior-historical.md](../auto-core/plans/0029-behavior-historical.md), and design documents in numbered `../auto-core/plans/NNNN-*.md`; user documentation in [README.md](./README.md).

## Overview

`@opencode-ai/auto` is the general CLI shell (bin `opencode-auto`): the init/continue/amend/plan/close/run/fix/reset/check/status subcommands and argument parsing are concentrated in `src/index.ts`, and all mechanisms are implemented in the core library `@opencode-ai/auto-core` (workspace dependency, subpath imports, driving opencode through its v2 SDK interface for per-task automated execution). Comments and user-facing messages are written in English, using the terms in [../auto-core/docs/glossary.md](../auto-core/docs/glossary.md).

## Commands (run inside this package directory)

- `bun run dev -- <args>` — run the CLI directly from source.
- `bun run build [--target <platform>]` — produce the standalone executable `dist/opencode-auto`.
- `bun typecheck` — `tsgo --noEmit`.
- `bun test` — runs `test/` (CLI parsing / e2e).

## Package boundary

- This package contains only the CLI shell (`src/index.ts`), build scripts, and e2e tests; core src, templates, and design documents live in `../auto-core`.
- **The core does not know shells**: never duplicate core logic here; when a need touches a core extension point, change `../auto-core` first (shell differences are injected via the `setShellProfile` profile or `registerTemplate`).

## Build conventions (developing this program)

- **Templates must keep the `with { type: "file" }` import** (via the `@opencode-ai/auto-core/templates/*` subpath) — the only way to embed them into the binary at compile time. New init copy templates → the `templates` mapping in `src/index.ts`; prompt/mode templates are changed in the `../auto-core` package.
- `src/templates.d.ts` provides path-string types for `*.md` / `*.json` imports; do not remove `resolveJsonModule: false` from `tsconfig.json`.

## Config semantics of init / amend / fix / reset (read before changing)

- `init` defaults to **stateless full overwrite**: `.opencode/auto/config.json` is decided solely by the parameters given this time, with absent keys falling back to `CONFIG_DEFAULTS` (the flagless hand-edited keys `acceptanceGate` / `build` are kept). The only watershed is `base = amend ? existing : { ...CONFIG_DEFAULTS, ...handEdited }` in `src/index.ts`; `--amend` and `continue` take the existing config as the baseline. The two baselines load differently (plans/0052 D4): an amend carries every stored key over, so it loads strictly (`loadProjectConfig`); a full overwrite discards them, so `loadOverwriteBaseline` tolerates retired keys and `init` names each dropped one with its value.
- `amend` (plans/0052 D25) is the amend baseline as a command of its own, sharing init's block (`amendCommand`): config flags only (`CONFIG_FLAGS`; `-p`, `-f` and `--amend` are usage errors), refused without config.json or without a key, and it writes only what renders from the config (config.json, the contract, the AGENTS.md block) plus the round step — never `opencode.json`, `.gitignore` or the brief stub. `init --amend` stays until P3c.
- `fix` (plans/0052 D10/D11) takes no config flag and never resets a key: its rule table and boundary live in `../auto-core/src/config-fix.ts` (read its header before adding a rule). Hints that tell a person to change one key name `amend`; hints that tell them to refresh the contract or the AGENTS.md block, or to clear a retired key, name `fix` — never a flagless `init`, which resets every other key (DF8). A strict config failure appends `fixHint(dir)`.
- **Validate, then write** (plans/0052 D7): every refusal `init` can make — flag values, empty `-p`, mode, prefix guard, phase-directory sync (`plannedPhaseUnits`, the read-only half of `syncPhaseIndex`), prompt-library and intent-pack validation, and the commit-capability prerequisite (`commitIdentityProblem` in `../auto-core/src/git.ts`: inside a git work tree, git must be able to commit there, so a missing user.name/user.email refuses init; plain init only — `--amend`/`continue` retire with P3c and are not covered) — happens before the overwrite guard and the first write. A new check goes there too, never after `saveProjectConfig`. Plain `init` also writes the wider `.gitignore` set via `ensureInitGitignore` (`../auto-core/src/gitignore.ts`: the driver workdir, local-only files and nested git repositories); `reset`'s `removeGitignoreEntries` removes exactly that set.
- The phase-index prefix guard (completed phases in `docs/R-NN/phases.md` order must prefix the new value) judges the **effective value of this run** (`effectivePhases`), not "whether `--phases` was explicitly given" — otherwise a no-arg init would silently reset a staged project's phases to `"m"` and destroy the round layout. Any new path that affects `phases` must preserve this rule.
- The cleanup list and boundary rules of `reset` are documented in the header comment of `../auto-core/src/reset.ts` — read that entire comment before changing the list: only the config layer is cleaned, directories are always removed with `rmdir` (reclaimed only when empty, never `rm -r`), and the `opencode.json` shared with the main program is deleted only after a byte-for-byte comparison against the template.
- `plan` (plans/0053 D14–D15) shares `run`'s option machinery: `refuseFrozenFlags` (config flags with the amend hint), `parseSessionFlags`, `loadRunConfig`, `logRunBanner` and the `runOptions` builder live above the two command blocks and are the single place to change them. `plan` refuses run-only options (`--dryrun`, `--wait-between`, `--max-sessions`) and takes its planning input as `-p <text>` or `--file <path>` (mutually exclusive, non-empty, `--file` a regular readable file), then holds the run lock itself (`acquireRunLock(dir, "plan")`, re-entered by `runAll`), prints a `planPrelude` stop's lines and exits with its code, and otherwise calls `runAll` with `stopBefore: "execute"` and `planInput`. run refuses `-p`/`--file`; init/continue/amend refuse `--file`. `plan --force-close <ref> --reason <text> [close flags]` (plans/0053 D28) validates close's argument set (the three canonical ref shapes, the required one-line reason, the change pair; the close-family flags without `--force-close` are usage errors, and every other command refuses `--force-close` with a pointer to plan), then runs `closeUnit` under the same plan lock before the prelude: refused → 1 with nothing done, failed commit → 2, closed → the normal plan flow with plan's exit code.
- `close <ref> [dir] --reason <text> [--cascade] [--commit-changes | --stash-changes]` (plans/0053 D17–D22, D30) closes a unit without completing it (`closeUnit` in `../auto-core/src/close.ts`): the ref comes first (`positional[0]`, overriding the global directory rule; the shell validates the three canonical shapes — a subtask-shaped ref is a usage error naming them), only `CLOSE_FLAGS` are accepted (`--commit` gets the whole-name parsing notice naming `--commit-changes`/`--stash-changes`), and the order is argument checks → legacy-layout check → strict config load → `acquireRunLock(dir, "close")` → `closeUnit` → its `lines` printed (stdout when closed, stderr otherwise); exit 0 closed / 1 refused or usage / 2 commit or close-out failure. No confirmation prompt (the explicit ref and required reason are the confirmation); the undo is `git revert <sha>` of the close commit, printed in the output and valid before anything else runs — there is no `reopen`. `plan --append` (plans/0053 D23) is a plan-only boolean flag, refused by every other command with a pointer to plan, and a usage error without input.
- The run lock (`../auto-core/src/lock.ts`, auto-core plans/0053 D3): `init`, `continue`, `amend`, `fix` and `reset` write what a running driver reads, so they refuse with exit 1 while `liveRunLock` finds another process holding `.auto/run.lock` — one check after the legacy-layout check, ahead of every command block; `-f` does not override it. `run` takes the lock inside `runAll`; `check` and `status` never lock, and `status` prints a live lock first. A new command that writes the config layer or the round setup joins that check.
- The destructive paths (`reset`, `fix` when it has fixable findings, and `init` overwriting an existing config) pass through the worktree-cleanliness gate (`../auto-core/src/clean.ts`) and the interactive confirmation (`confirm.ts`) before executing; `-f/--force` skips both; both checks must run before the first write to disk.
