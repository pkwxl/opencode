# Core/shell contract (package boundary and merge flow)

> AGENTS.md keeps only navigation; the core/shell boundary, dependency direction, difference-injection extension points, branch merge flow, the new-shell onboarding checklist and the agent adapter onboarding checklist are concentrated in this file. Effective since the physical package split (phase two); later new shell branches onboard per this file.

## A. Boundary

| Package | Role | Contents |
|---|---|---|
| `packages/auto-core` (`@opencode-ai/auto-core`, no bin) | **Core** | Mechanisms (runner/loop/resume/numbering/phases/plan/close/script/git/protect/config/config-fix/brief/server/mode/prompt/template/knowledge/interactive/log/shell/check) + built-in templates (`templates/`) + design documents (`docs/`) |
| `packages/auto` (`@opencode-ai/auto`, bin `opencode-auto`) | General CLI shell | `src/index.ts` with init/amend/plan/close/run/fix/reset/check/status/models subcommands, build scripts, CLI parsing/e2e tests |
| `packages/<name>` (`@opencode-ai/<name>`, bin `<bin>`) | Simple CLI shell (per shell branch) | Shape and artifact naming are decided by each shell branch, using the existing simple shell branch as reference; the core does not record specific names |

Decision rule: session pipeline, state-file protocol, prompt rendering, acceptance/commit mechanisms belong to the **core**; CLI shape (subcommands or not, usage text, argument parsing and config fixation policy, build artifact naming) belongs to the **shell**.

## B. One-way dependency

- Shells import `@opencode-ai/auto-core/*` (core `package.json` `exports`: `"./*": "./src/*.ts"`, `"./templates/*": "./templates/*"`); templates are imported from `@opencode-ai/auto-core/templates/<file>` via `with { type: "file" }` (embedded into the binary at compile time).
- **The core does not know shells**: packages/auto-core must not import any shell package; default behavior = the general shell's status quo — with no profile set, core messages are byte-identical to historical behavior.
- **Shells never depend on each other**: shell packages never import one another; they share only the core.
- Each shell package must ship its own `src/templates.d.ts` shim (path-string types for `*.md`/`*.json` imports; without it, cross-package template imports all go red); do not remove `resolveJsonModule: false` from `tsconfig.json`.

## C. Difference injection (shell extension points)

Shell differences are injected exclusively through the following extension points; **shell branches must not modify packages/auto-core** — core needs get their extension points added on the auto-core branch first:

1. `setShellProfile` (src/shell.ts): message program name (program/bin), recovery guidance for a missing agent contract (agentRecovery: `"init"` | `"startup"`), log audit semantics (auditLog), the agent profile (agent: `{ name, host }` — the `AgentHostFactory` that starts the shell's coding agent; absent = the built-in adapter the project picks — `RunAllOpts.agent` / config `agent` (`opencode` by default, or `claude`: the headless adapter `claudeHost` from `agent/claude/host`, plans/0041), overridden per run by `OPENCODE_AUTO_AGENT`; selection lives in `agent-choice.ts`; what the agent cannot do is read from its client capabilities and degraded by the core at run start, plans/0040), and `configDir` (the model registry's operator-layer directory name under `$XDG_CONFIG_HOME`, default `opencode-auto`, plans/0055); set once at shell entry startup. Example for a simple shell: `{ program: "<shell name>", bin: "<bin>", agentRecovery: "startup", auditLog: true }`.
2. `registerTemplate` (src/template.ts): registers additional prompt templates and tier-1 protocol markers; takes precedence over built-ins, with target-directory overrides highest; `_partials` refuses wholesale registration — individual shared-partial sections register via `registerPartial(name, text, markers?)`, and target-directory `_partials.md` overlays of protocol-sensitive sections are validated against tier-1 markers (same enforcement as template-level markers). Project-local override surfaces need no shell code: `.opencode/auto/prompts/` (templates), `.opencode/auto/modes/` (modes), `.opencode/auto/intents/` (intent packs, since M1; loaded by the core at preflight, same-named file replaces the whole built-in pack). **Trust boundary** (same as modes, which set the precedent): these overlays are project-local files injected verbatim into prompts, so a checked-out target repository that ships `.opencode/auto/` is trusted exactly as far as its own `AGENTS.md` and source are — the core validates only structure (tier-1 protocol markers of templates and partial sections, pack headings), never intent. Running the driver on an untrusted repository means running that repository's instructions; review `.opencode/auto/` like any other code before a run.
3. Parameter passing: shell CLI parsing results flow in via runAll Opts / runTool arguments (newSession, managed server handle, testByDriver/handoverTest and other existing switches).

A shell's `plan` command calls it under the run lock before `runAll`, prints a stop's lines and exits with its code (`packages/auto` in A6). `roundCloseLines`' failure heading no longer names `continue`.

- **The `plan` command** (A6, D14–D15): shell-side, `packages/auto` `plan [dir] [-p|--prompt <text> | --file <path>] [session flags]` is the reference. The option machinery is shared with `run`: one frozen-flag refusal (`refuseFrozenFlags`), one session-flag parse, one config load + mode check, one banner and one `runAll` options builder serve both commands; `plan` refuses run-only options (`--dryrun`, `--wait-between`, `--max-sessions`) and run refuses `-p`/`--file` (the planning input), while init and amend refuse `--file`. The planning input is checked (mutually exclusive, non-empty, `--file` a regular readable file) before the lock. Order: legacy-layout check → strict config load (`fixHint`) → mode check → `acquireRunLock(dir, "plan")` (re-entered by `runAll`) → `planPrelude` (a stop prints its lines and exits with its code) → `runAll` with `stopBefore: "execute"` and `planInput`. The command-line surface is the shell's to shape; the core needs nothing beyond A1–A5.

**Changes shells must absorb when refreshing the core snapshot (model registry and tier routing, `plans/0055`, 2026-09-26):**

## D. Branches and merge flow

| Branch | Responsibility |
|---|---|
| `auto-core` | Core development branch (packages/auto-core + packages/auto general shell; the general shell evolves with the core branch) |
| `migrate` | Simple shell branch — **frozen (2026-09-22)**: never changed, never merged into |
| `auto` | Former integration branch — **frozen (2026-09-22)**: never changed, never merged into; no longer the release base |

- **Core changes land only on the auto-core branch**, the single merge target; verification runs on it with both packages (auto-core + auto).
- The frozen branches keep the core snapshot they have; they receive no `git merge auto-core`. The simple shell there stays the reference for shell shape (E), not a consumer to keep in sync.
- A new shell branch, if one is ever started, refreshes its core snapshot by merging auto-core (packages/auto identical on both sides, conflict-free by construction).

## E. New-shell onboarding checklist

Create `packages/<name>` (bin named independently), using the existing simple shell branch's package as reference:

1. `package.json`: name `@opencode-ai/<name>`, bin `<independent name>`, `dependencies: { "@opencode-ai/auto-core": "workspace:*" }` (omit if the shell does not import the sdk directly), typecheck/test/build scripts.
2. Entry point calls `setShellProfile({ program, bin, agentRecovery, auditLog })` to set the shell profile.
3. Ship its own `src/templates.d.ts` shim and `tsconfig.json` (copy the shell package's version).
4. Ship its own `script/build.ts` (artifact `dist/<bin>`); templates keep the cross-package `with { type: "file" }` import.
5. Additional prompt templates are registered via `registerTemplate` (protocol-sensitive templates provide markers).

## F. Agent adapter onboarding checklist

A coding agent reaches the driver through one interface, `AgentClient` / `AgentHost` in `src/agent/types.ts` (frozen in MA.1; `src/agent/opencode/` and `src/agent/claude/` are the references, plans/0039 and plans/0041). Two ways in:

- **Shell-supplied** (no core change): a shell passes `setShellProfile({ agent: { name, host } })` with its own `AgentHostFactory`. It then drives every run of that shell, above `OPENCODE_AUTO_AGENT` and the config (C.1). To let the model registry's `adapter` field name it too, register the same factory with its capabilities and default `bin` through `registerAgentAdapter(name, { host, capabilities, bin? })` (plans/0055 §8.8) — **a shell adds an adapter by registration, never by patching the core**.
- **Built in** (core change, auto-core branch): the steps below.

1. **Client** — `src/agent/<name>/client.ts` implements `AgentClient`: map the agent's output onto the `AgentEvent` vocabulary, declare `AgentCapabilities` truthfully (`resume`, `fork` none|session|message, `steer`, `abort`, `question`, `permission`, `history`, `usage` tier), and supply `AgentErrorPatterns` (overflow / quota / auth / rate / transient) so error classification and the model-failback ladder work. Transport concurrency stays inside the adapter (MA.1 F12).
2. **Host** — `src/agent/<name>/host.ts` exports an `AgentHostFactory`: check the agent is installed (fail with an install hint), start or connect, and implement `syncContext` / `restart` / `close`. Warn about `AgentHostOptions` it cannot honour (as `claudeHost` does for `--server`).
3. **Usage tier** — pick the honest `UsageSource` tier (plans/0038): events, reported, estimated or none. The tier decides how session reuse, steer, test handover and the failback window behave.
4. **Contract surface** — the driver renders one contract (`.opencode/agent/auto.md`, `CONTRACT_AGENT`) and one permission policy (`opencode.json`). Translate both when the process starts rather than keeping an agent-specific copy (`agent/claude/contract.ts` is the pattern). `AGENTS.md` must reach the agent as project context.
5. **Degradation** — missing capabilities fall back through `src/capability.ts` at run start. A new capability flag, or a configuration with no fallback, needs a rule and a note there.
6. **Registration** — extend `AgentChoice` (`switches.ts`, with its env parse and messages), `agentOf` (`config.ts`), `chooseAgent` (`agent-choice.ts`), the host module in `DOMAIN_ENTRIES` (`test/import-direction.test.ts`), and the shell's `--agent` validation and help text (`packages/auto`); a shell-side adapter without a core change registers through `registerAgentAdapter` (above), which the model registry's `adapter` field accepts by name.
7. **Verification** — adapter unit tests on recorded output (as `test/agent-claude.test.ts` does), the fake-client suite staying green (`test/fixtures/agent.ts`), and one real round on a sample project compared against opencode for artifacts and flow log (plans/0042 is the template).
