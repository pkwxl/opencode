# opencode-auto target directory templates

Maintainer documentation for this directory. Only the first two files below are copied into a
target project (init writes them); the rest are embedded into the binary at compile time and
rendered or materialized by the tool:

- `opencode.json` — permission allowlist: the execution agent's bash/edit permission rules
  (person-editable after init; `fix` restores it only when it is missing). The shipped copy is
  full-trust by design — the bash table's `"*": "allow"` wildcard with no model pin (session
  models come from the driver's own routing and the model registry layers): driver runs are
  unattended and a permission request blocks the run rather than guarding it, so containment
  lives in branch isolation, the clean-tree gates and the unified commit, not the bash table.
  The narrower patterns beside the wildcard are the ready-made starting point for a person who
  deletes it and wants a tighter posture.
- `.opencode/agent/auto.md` — the non-interactive execution agent contract (same init-copy and
  restore rule).
- `prompts/` — session prompt templates, embedded via the `with { type: "file" }` imports in
  `src/template.ts`; same-named `.md` files under the target's `.opencode/auto/prompts/` override
  them (`_partials.md` merges per section), and shells register additional templates/partials via
  `registerTemplate`/`registerPartial`. Protocol-sensitive templates and partial sections carry
  tier-1 markers an override must keep (see `src/template.ts`).
- `intents/default.md` — the built-in intent pack; `modes/migrate.md` — the built-in mode;
  `bundles/` — the shipped intent bundles (cleanroom / faithful / faithful-lean) that
  `init --intent <name>` materializes into `.opencode/auto/`.
- `README.md` — this file.

Task units in the target directory (not template files; written by a formulation session or by
hand): one `docs/R-NN/` per round (a phased round is established by `transfer` — in m mode by
`plan`), and under it one `P<nn>-<type>/` per phase; the phase's task index `tasks.md` has one
line per task, `- [ ] T-NNN <title>`; the task content is in `docs/T-NNN/todo.md` (a title line,
a `Phase:` field line, the three sections `## Goal` / `## Scope` / `## Acceptance`, and a last
line `<!-- auto: eof -->`). A task is completed by the driver renaming `todo.md` to `done.md` and
ticking the index line; in_progress/blocked/attempts are run state, kept in `.auto/units.json`
(not in git). The subtask list is in `docs/T-NNN/subtasks.md`, generated by the decompose session
and ticked by the driver. Each task's wrap-up session verifies it against its acceptance
criteria: a `Result: FAIL` opens the bounded fix loop (fix rounds run while progress holds; two consecutive no-gap rounds block, plans/0146) before the run
blocks for a person, who accepts the verdict with `close` (or plans the rework).

## Usage

```sh
opencode-auto run <dir>
# or connect to an existing long-running server:
OPENCODE_AUTO_SERVER=http://127.0.0.1:4096 opencode-auto run <dir>
# wait for a human to answer questions and permission approvals on the command line (minutes, 1-60, default 1): a non-permission
# question is auto-answered on timeout; answering a permission request with allow/yes/y etc. grants it, a timeout or any other answer blocks:
opencode-auto run <dir> --wait-answer 5
# verbose (boolean): print every message part in the session (text, tool calls, reasoning, steps, etc.) and each assistant message's context usage/share,
# timestamp every output line, and list newly changed files from git status every 10 seconds (nested .git sub-repositories included) to follow progress:
opencode-auto run <dir> --verbose
# interactive: side-channel interaction (mutually exclusive with --verbose) — the terminal keeps clean output and waits for input;
# Enter sends the input as an extra message to the active session (dropped when there is none); the log file still keeps the full verbose record:
opencode-auto run <dir> --interactive
```

Constitutional keys are fixed into `.opencode/auto/config.json` by init only and changed per key
with `amend` — passing them to `run` is a usage error. Notably the task pipeline key is
`--subtask off|auto|true|ondemand` (set at init/amend): `off`, the default, runs whole-task
sessions per task under the standing context-handover protocol (a session hands its context
over to a fresh session mid-task when the budget demands it); `true` runs the planned decompose
pipeline (a decompose session writes `subtasks.md`, then one fresh session per subtask); `auto`
decomposes adaptively; `ondemand` is `off`'s permanent synonym (the mode that once carried the
protocol alone — merged into `off`, plans/0130). Committing cannot be turned
off: the unified commit after each session is the completion condition, and any `--commit` form
is a usage error.

## Human intervention

1. When the driver hits a block (a permission-related question / a permission approval / session-error retries exhausted / a session that ends without marking completion), it stops by itself
   with exit code 2 and records the problem in the run log.
   A non-permission question is auto-answered by the driver ("Decide how to proceed on your own, ...") and the run continues;
   only asking the same question again stops the run to wait for a human.
   With `--wait-answer [1-60]` (1 minute when no value is given), questions (permission questions and
   permission approvals included) first wait for a human answer on the command line (confirm with Enter): answering a permission request with allow/yes/y etc.
   grants it and continues, while a timeout or any other answer denies it and blocks; a non-permission question with no answer before the timeout is auto-answered;
   without this option, non-permission questions are auto-answered at once and permission requests block directly.
2. A block is not a question but something to handle outside the session (such as allowing a permission or fixing the environment).
   Once a human has looked into it and handled it, just re-run: the driver opens a fresh session for the task and tells the agent
   the problem was resolved outside the session and not to ask again.
3. A failed task (two consecutive fix rounds closed no gap, still `Result: FAIL`) also stops with exit code 2: accept it with
   `opencode-auto close <T-NNN> <dir> --reason <text>` or plan the rework, then re-run.
4. Re-run `opencode-auto run <dir>`; the driver opens a fresh session for the task and continues with its history.
5. Once every task is complete (`done.md`), the driver exits with code 0.

Check progress: `opencode-auto status <dir>`
