# opencode-auto target directory templates

Maintainer documentation for this directory. Nothing here is copied into a
target project any more: every file is embedded into the binary at compile
time and rendered or materialized by the tool. (The two init-copy files this
directory once shipped — the host permission allowlist `opencode.json` and
the non-interactive agent contract `.opencode/agent/auto.md` — are gone with
plans/0296: the host's configuration is never the tool's file, and the
claimant sessions of the executor protocol bring their own host.)

- `prompts/` — session prompt templates, embedded via the `with { type: "file" }` imports in
  `src/template.ts`; same-named `.md` files under the target's `.opencode/auto/prompts/` override
  them (`_partials.md` merges per section), and shells register additional templates/partials via
  `registerTemplate`/`registerPartial`. Protocol-sensitive templates and partial sections carry
  tier-1 markers an override must keep (see `src/template.ts`).
- `intents/default.md` — the built-in intent pack; `modes/migrate.md` — the built-in mode;
  `bundles/` — the shipped intent bundles (cleanroom / faithful / faithful-lean) that
  `init --intent <name>` materializes into `.opencode/auto/`.
- `README.md` — this file.

Task units in the target directory (not template files; written by a formulation session or by
hand): one `docs/R-NN/` per round (a phased round is established by the person's `transfer`
operation — in m mode by `plan`), and under it one `P<nn>-<type>/` per phase; the phase's task
index `tasks.md` has one line per task, `- [ ] T-NNN <title>`; the task content is in
`docs/T-NNN/todo.md` (a title line, a `Phase:` field line, the three sections `## Goal` /
`## Scope` / `## Acceptance`, and a last line `<!-- auto: eof -->`). A task is completed by the
coordinator renaming `todo.md` to `done.md` and ticking the index line; in_progress/blocked/
attempts are run state, kept in `.auto/units.json` (not in git). The subtask list is in
`docs/T-NNN/subtasks.md`, generated by the decompose session and ticked by the driver. Each
task's verify share checks it against its acceptance criteria: a `Result: FAIL` is a finding for
the person at the round's close (the no-fix rule), never a repair input.

## Usage

The tool is pull-mode only (plans/0279, 0296): the daemon serves the executor
protocol and the person's operations; every unit of model work belongs to a
coding-agent session that claims a grant.

```sh
# the daemon (registers projects, serves the executor routes and the ops):
opencode-auto-server serve
# the target-side commands (init, amend, fix, status, close, …):
opencode-auto init <dir>
# a claimant session speaks the routes — the manual floor is prompts/executor.md:
#   ready / claim / brief / report / heartbeat / release over
#   POST /projects/<project>/executor/<route>
```

The protocol's single source is [docs/protocol.md](../docs/protocol.md); the
daemon's own HTTP surface is documented in the server package. Constitutional
keys are fixed into `.opencode/auto/config.json` by init only and changed per
key with `amend`. Committing cannot be turned off: the unified commit after
each share is the completion condition, and any `--commit` form is a usage
error.

## Human intervention

The person brackets every boundary (P2): the gates derive from document state
(the survey's human gate, the project-start condition), and the person's acts
are document writes and the daemon's deterministic operations — `transfer`
(the boundary advance), `clarify` (the gate release), `reconcile` (the
dead-letter reconciliation). A claimant that hits a person-necessary cause
ends its session at `blocked`; the menu's `pending` rows name the awaiting
gate and its document. A failed verify (`Result: FAIL`) is the person's
finding at the round's close.
