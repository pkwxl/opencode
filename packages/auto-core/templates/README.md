# opencode-auto target directory template

Copy the two files in this directory to the target project root (init writes them into the target directory; the rounds under `docs/` are plan's — `plan` establishes them):

- Task units (not template files; written by a planning session or by hand): one `docs/R-NN/` per round, and under it one
  `P<nn>-<type>/` per phase; the phase's task index `tasks.md` has one line per task, `- [ ] T-NNN <title>`;
  the task content is in `docs/T-NNN/todo.md` (a title line, a `Phase:` field line, the three sections `## Goal` / `## Scope` /
  `## Acceptance`, and a last line `<!-- auto: eof -->`). A task is completed by the driver renaming `todo.md`
  to `done.md` and ticking the index line; in_progress/blocked/attempts are run state, kept in
  `.auto/units.json` (not in git). Acceptance work is planned as tasks (as in the v acceptance phase): when the verdict line of the
  task report `docs/T-NNN/report.md` says `Result: FAIL`, the driver commits, marks the task blocked
  and stops the run for a human to handle (rename it to done.md to accept the verdict, or insert a fix task before it in tasks.md),
  then re-run. The subtask list is in `docs/T-NNN/subtasks.md`, generated by the decompose session and ticked by the driver.
- `opencode.json` — permission allowlist: safe read-only/build/test commands are allowed automatically; any other bash command
  is escalated to human approval (which triggers the blocking flow).
- `.opencode/agent/auto.md` — the non-interactive execution agent contract.

## Usage

```sh
opencode-auto run <dir> --agent auto
# or connect to an existing long-running server:
OPENCODE_AUTO_SERVER=http://127.0.0.1:4096 opencode-auto run <dir> --agent auto
# wait for a human to answer questions and permission approvals on the command line (minutes, 1-60, default 1): a non-permission
# question is auto-answered on timeout; answering a permission request with allow/yes/y etc. grants it, a timeout or any other answer blocks:
opencode-auto run <dir> --agent auto --wait-answer 5
# verbose: print every message part in the session (text, tool calls, reasoning, steps, etc.) and each assistant message's context usage/share,
# timestamp every output line, and list newly changed files from git status every 10 seconds (nested .git sub-repositories included) to follow progress:
opencode-auto run <dir> --agent auto --verbose true
# interactive: side-channel interaction (mutually exclusive with --verbose) — the terminal keeps clean output and waits for input;
# Enter sends the input as an extra message to the active session (dropped when there is none); the log file still keeps the full verbose record:
opencode-auto run <dir> --agent auto --interactive
# commit: unified commit after each session (always on; the agent has no commit rights) — whenever a session ends and the driver has written its state,
# the driver recursively commits every change (nested .git sub-repositories first, then this repository) with messages carrying the task number and phase,
# giving per-subtask change history and per-session rollback. Committing is a completion condition; `--commit false` was
# retired on 2026-09-15 (it is a usage error); like the other constitutional keys, this key is fixed only at init:
opencode-auto init <dir> --commit true
# new-session-subtask: strictly one fresh session per subtask (subtasks are the - [ ] check items of docs/T-NNN/subtasks.md),
# bounding the context size of any one session; each subtask session is judged by its check item being ticked;
# once all subtasks are done, a wrap-up session updates docs and commits remaining changes, then the driver renames the task to done.md:
opencode-auto run <dir> --agent auto --new-session-subtask
```

## Human intervention

1. When the driver hits a block (a permission-related question / a permission approval / session-error retries exhausted / a session that ends without marking completion), it stops by itself
   with exit code 2 and records the problem in the run log.
   A non-permission question is auto-answered by the driver ("Decide how to proceed on your own, ...") and the run continues;
   only asking the same question again stops the run to wait for a human.
   With `--wait-answer [1-60]` (1 minute when no value is given), questions (permission questions and
   permission approvals included) first wait for a human answer on the command line (confirm with Enter): answering a permission request with allow/yes/y etc.
   grants it and continues, while a timeout or any other answer denies it and blocks; a non-permission question with no answer before the timeout is auto-answered;
   without this option, non-permission questions are auto-answered at once and permission requests block directly.
2. A block is not a question but something to handle outside the session (such as allowing a permission or fixing the environment).
   Once a human has looked into it and handled it, just re-run: the driver opens a fresh session for the task and tells the agent
   the problem was resolved outside the session and not to ask again.
3. Re-run `opencode-auto run <dir>`; the driver opens a fresh session for the task and continues with its history.
4. Once every task is complete (`done.md`), the driver exits with code 0.

Check progress: `opencode-auto status <dir>`
