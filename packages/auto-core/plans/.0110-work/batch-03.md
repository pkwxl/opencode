## 0020-auto-resolve-design
- Date: 2026-09-12 (Status: "Implemented (2026-09-12; T-001..T-008 all landed …)"; git add-date 2026-09-19, bulk import)
- Trigger: One marker `AUTO-DECISION` carries two things of completely different natures (pure engineering discretion vs suppressed questions); category 2 drowns in category 1 and the driver is completely blind to both — after a 24-task round you cannot know how often the system decided for humans without digging through logs.
- Rulings:
  - AUTO-DECISION = autonomous decision among reasonable technical options; regular engineering log, no terminal highlight (§B stance 1)
  - AUTO-RESOLVE = decision that should have been asked of the user but was auto-answered; highlighted and pinned at task end (§B stance 2)
  - The question strategy and the AUTO-DECISION recording obligation advance and retreat together, switched by a single switch (§B stance 3)
  - Under ask mode AUTO-DECISION is "not required", not "a lowered bar"; no self-assessment middle tier (§B stance 4)
  - Only fallback auto-answers count as AUTO-RESOLVE; human answers under `--wait-answer` and dryrun pre-checks do not (§B stances 5–6)
  - Display tiering reuses the existing `vlog` channel; no new switch for "how much to show" (§B stance 7)
  - AUTO-DECISION does not enter the ledger (no line-level persistence); the persistent trail is the marker lines + the report.md section, both in git (§B stances 8/10)
  - A separate file `.auto/resolves.json`, not merged into `stats.json` (stats has high-frequency heartbeat rewrites) (§B stance 9)
  - Ledger write failures are fully silent and never affect flow or exit codes (§B stance 11)
  - Discrimination criterion = who the decision right over a divergence point originally belongs to (user → AUTO-RESOLVE, AI → AUTO-DECISION); when unsure, mark AUTO-RESOLVE (§C)
  - parseResolveLine is fault-tolerance first: a malformed line without arrow still counts, flagged ⚠ in the report (§D)
  - `OPENCODE_AUTO_ASK` switch: default `off` is byte-for-byte the status quo; `on` actively asks user-owned divergences and driver observation becomes the authoritative complete source (§E)
  - Render-side injection takes a unified exit (`renderPrompt` injecting `ask`) rather than per-function pass-through across 23 templates (§E, T-002)
  - Ledger schema v:1; total cap 512 entries FIFO; dedup key = source + task + normalized question; AUTO-DECISION persists one integer per task (T-006 addendum to "does not enter the ledger") (§F)
  - Report tiers: in-session immediate ⚑ line; task-end pinned block capped at 8 entries; phase/round count lines; AUTO-DECISION collapsed into counts and never displayed at phase/round level (§H)
  - Wrap-up closed loop: the driver-observed auto-resolve list is injected into the wrap-up prompt as its 4th numbered item; report.md must contain every listed one (§I, T-007)
  - Use the `on` mode when auditable auto-resolve records are needed; the default mode's "unmarked" count is meaningful only for driver-observed cases (§K-1)
  - On false duplicate-question blocks, tighten `sameIssue` rather than abandon duplicate detection (§K-2)
  - If the highlight noisifies, tighten the criteria copy rather than add a switch (§K-3)
  - Mode choice is a human judgment; there is no "auto-detect plan completeness then switch modes" (§K-5)
  - The ledger is a local-machine run footprint, not a source of truth; marker lines and the report section are the persistent trace (§K-6)
  - Two concurrent runs in the same directory are unsupported; manual rerun of the same task requires `rm .auto/resolves.json` (§K-7/8)
  - Under `--commit false` the AUTO-DECISION count runs large — accepted boundary, the count is a gut-feel indicator not a source of truth (§K-10)
  - Zero breakage of core invariants: exit codes, driver-exclusive writes, unified commits, session forking all unchanged; the new switch reads the environment only (§K-11)

## 0021-commit-boundary-design
- Date: 2026-09-14 (Status: "approved for implementation 2026-09-14"; D7 dated 2026-09-15)
- Trigger: Generalize the prior-knowledge extraction's "persisted and committed" protocol into a universal completion check: a unified-commit failure previously only "warned without blocking", so completion had no enforced git boundary.
- Rulings:
  - Done ⟺ persisted and committed: a unit that modified anything git tracks is complete only once a commit has formed; unified-commit failure → block and halt (exit 2) pending manual attention (§1.1)
  - Clean baseline at unit start; dirty state not attributable to the driver → block and hand to a human (§1.2)
  - SHA baseline per repository at unit start; close-out requires clean tree + every commit in baseline..HEAD carrying the `Auto-Stage` trailer; `Auto-Nested` covers the full set of nested repositories (§1.3)
  - No tracked changes → no empty commit (commitTree skips unchanged repositories) (§1.4)
  - git commits are the factual boundary of logical isolation between tasks; audit/rollback granularity = session/unit (§1.5)
  - Gate inactive under `--commit false` / dryrun / non-git environments (§1.6; narrowed by D7 to dryrun/non-git)
  - D1: any commit failure blocks and halts; no automatic retry — the interrupted commit on the blocked path is the natural single retry
  - D2: the gate is attached at every post-session commit point, not just the completion-check boundary
  - D3: hidden-task ③ supplementary commit and ④ dirty block generalized to all standalone hidden tasks
  - D4: Auto-Nested records the full nested set + external-commit detection via the `Auto-Stage` trailer criterion
  - D5: run-startup dirty state left by a human blocks (no longer absorbed); driver-exclusive state leftovers (PLAN.md/CURRENT.md) → carryover self-healing supplementary commit
  - D6: session-recovery fidelity is a separate follow-up project (plans/0022) using this mechanism's unit clean baseline as the rollback anchor
  - D7: `--commit false` retired (2026-09-15, user decision) — the commits-off tier conflicts with the completion check, clean gate, SHA baseline and rollback anchor; entry-layer soft retirement (CLI occurrence = usage error exit 1; config `commit: false` fails strictly); the code-side gate stays temporarily, unreachable
  - The `Outcome` gains a `dirty` variant: writes nothing to PLAN.md and makes no interrupted sweep commit — the authority over git state belongs to a human (§3.2)
  - `spec.commit` failure → blocked with no retry-with-feedback: "reopening a session for a git failure is pointless" (§3.2)
  - Recovery resume (active record / session reuse) is exempt from the clean gate — a known limitation backstopped by the close-out trailer check (§3.2/§6)
  - Multiple driver commits within a unit are legal; unitViolations checks only the trailer, with no count limit (§6)
  - Residue from reverting judge overreach → exception scene handed to a human, consistent with "overreach is an exception" (§6)
  - addendum (2026-09-15): on the test-handover path the dirty-exemption limitation is resolved — the handover point makes two driver commits, the new session faces a clean worktree (§6, pointing to 0023 D3)
  - correction (fixed 2026-09-15): the driver-exclusive state-file whitelist must resolve symlinks (`driverStateFiles`) — the literal list failed wholesale under the phase layout; interruption-recovery disk writes moved after the startup clean gate, booked by the `housekeeping` commit (§6)

Unified-commit failure → **block and halt (exit code 2), pending manual attention**, no longer \"warn without blocking\"." (§1.1)
  - "all information the unit depends on is fixed by the previous commit or produced during the unit itself" (§1.2)

## 0022-session-recovery-fidelity-design
- Date: 2026-09-14 (Status: "initiated 2026-09-14, design finalized; implementation completed 2026-09-15"; revisions 2026-09-15/17, promotion note 2026-10, provenance note 2026-10-03)
- Trigger: User requirement (2026-09-14) that on interruption recovery strictly reuse the live session's id, append at most one `continue` prompt, meet an extremely high fidelity bar, else `git stash` rollback and rerun from the run-start state — plus a field-log audit of two target directories (~23MB, 2026-09-10..15) that found the six recovery paths incoherent.
- Rulings:
  - Fidelity bar: session-id reuse allowed only when "post-recovery behavior ≈ an uninterrupted continuation" can be argued rigorously; any uncertainty → no reuse, roll back (§1.1)
  - Minimal-continuation resume: the recovery prompt collapses to a single continue; per-step guidance stays in handover documents/status files (§1.2, §3.2)
  - Deterministic fallback: when fidelity cannot be guaranteed, stash-preserve + reset to the unit baseline and rerun in a new session — wasted work traded for determinism, explicit user choice (§1.3)
  - Audit verdict on the six paths: R1/R2/R4 meet the fidelity bar (prompt slimming only); R5 (session death keeping the dirty worktree) → rollback; R3 (document handover) demoted to best effort (§2)
  - Recording criteria tightened: active dispatch + unit ownership + unit baseline on record + model consistency (added 2026-09-15 from the field audit) (§3.1)
  - Old records lacking baseline/model fields are uniformly non-resumable — no half-hearted verification (§3.1, §5)
  - addendum (2026-09-17): the single continue gains a half-sentence commit-semantics clarification (COMMIT_CLARIFY: pre-interruption modifications may already be committed — verify with git log, do not redo) (§3.2)
  - Rollback protocol: per-repository `git stash push -u`; `git reset --soft <baseline>` reclaims this unit's driver commits; upstream-detected → stash only + warn; record to summary state; cold-start redo (§3.3)
  - Foreign commits → never rollback: dirty block and hand to a human; rollback reclaims only the driver's own in-unit changes (§3.3, §4.1-4)
  - R3 tightened with handover-boundary write verification (added 2026-09-15): after the handover session ends, the driver immediately verifies the document on disk ending `状态: 继续`; a miss triggers rollback at once (§3.3)
  - R4 fork continuation does not trigger rollback — fork is message-level copy, higher fidelity than document handover (§3.4)
  - Fork base-point independence made explicit (2026-09-15): on R1 recovery the digest fork base point is refreshed first; the blast radius of a reuse failure = a single subtask (§3.4)
  - Correction suggestions registered for adjacent mechanisms: handover-trigger decoupling to the single condition "context at limit" (implemented 2026-09-15 as 0023); quota-class errors must not burn new-session retries (§3.5)
  - Gate linkage: strict resume active = switch on ∧ `--commit true` ∧ not dryrun; off is byte-for-byte the status quo (§4.1-1)
  - No routing, no reuse: without OPENCODE_AUTO_MODEL configured the record has no model to write → counts as mismatch → rollback (§4.1-2)
  - Baseline-anchor tiering: task-entry baselines narrowed by subtask/phase-boundary baselines — smaller rollback radius (§4.1-3)
  - Mid-flight rollback-redo bounded to once each for executeWhole/runSubtask; a further failure takes the existing silent block (§4.1-5, S2-c)
  - resumeNote's third parameter is passed the gate value, not the bare switch (§4.1-6)
  - `--commit false` retirement echoed: with the gate off, strict resume spins idle as a whole (§4.1-7, citing 0021 D7)
  - 2026-10: `OPENCODE_AUTO_STRICT_RESUME` promoted to default-on per plans/0070 ruling P-1 (20-test coverage, 17+ days gray, no field incidents); `off` remains the emergency override; retiring the knob entirely is a later, separately ruled unit (status header)
  - addendum (2026-10-03): the raw audit file is ruled for deletion by the docs-governance round; its qualitative findings are folded into this document, the quantitative summary preserved in §6 (§6)
- Supersession: the status header's 2026-10 note supersedes the "default off, gradual rollout" ruling (promoted default-on by plans/0070 P-1); §3.5① notes the handover-trigger suggestion "implemented 2026-09-15, see plans/0023-test-handover-early-design.md"; §6 (2026-10-03) records the audit source file's deletion ruling and a path drift correction ("a path that has drifted").

## 0023-test-handover-early-design
