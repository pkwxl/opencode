## 0014-exit-resume-design
- Date: 2026-09-09 (Status: "implemented (2026-09-09)")
- Trigger: The `--interactive` resident input line treats any non-empty line as a steer to the active session; long unattended runs need a safe stop that neither runs on to the next blocking/completion point nor is a crude kill (which lands mid tool call, file write, or unified commit, leaving a dirty scene).
- Rulings:
  - Recognition: only the `--interactive` resident line; a line that after trim is exactly equal to `/exit` (case-sensitive, no normalization); intercepted after the empty-line check and before session forwarding — not sent to the session; no special-casing in the `pending` (ask/step-pause) state; the flag is set even with no attached session. (§2)
  - The flag is a one-time, per-process mark with no undo entry; repeated `/exit` input has no side effects; double Ctrl+C (exit 130) remains the immediate force-quit; the two do not conflict. (§2)
  - Hook points fully reuse step.ts's three boundary levels; each site inserts `maybeExit(boundary, label)` immediately after the existing `stepPause` call; at that point the state files are already the boundary's normal wrap-up result — `maybeExit` "stops here early" and does no extra saving. (§3)
  - `maybeExit` throws `ExitRequested` (an ordinary exception) and does not occupy `Outcome`'s `blocked`/`incomplete` channels (those mean "needs human intervention"); it skips `runTask`'s non-completion wrap-up; `runAll` catches it at top level and converts it to exit code `3` (new, distinct from `2`); the existing `finally` cleanup still executes. (§4)
  - Resume: no new recovery path — the exit point is itself one of the three existing boundaries, and resume fully reuses `resume.ts`'s existing semantics, byte-for-byte identical to the recovery path of a real crash/kill at that boundary. (§5)
  - Edge cases: non-`--interactive` runs zero behavior; single-phase `m` mode no phase boundary; `--subtask off/ondemand` no subtask boundary (one /exit waits at most until the current task completes); coexists with step mode (stepPause hard-waits first, then `exitRequested` is checked); `--dryrun`/`init`/`check`/`status` unaffected. (§6)
  - Out of scope: `/exit` typed while waiting in an ask/step pause is not special-cased; no interaction to cancel an already-set exit request. (§9)
- Supersession: none seen.
- Principle candidates (verbatim):
  - "`/exit` offers a "scheduled" exit: receipt is acknowledged immediately, but the actual pause is deferred to the next existing safe boundary, after which progress is saved as usual; the next run resumes precisely from the already-persisted state — fully isomorphic to the recovery path of any real crash/kill interruption, introducing no new recovery mechanism." (§1)
  - "/exit promises exit only in the "send a message" context, avoiding ambiguity in the "answering something else" context." (§2)
  - "those two channels mean "needs human intervention" (block reason written to PLAN.md, task reverted to pending); /exit is not that, and re-running needs no human to fill in any field." (§4)
  - "No new recovery path is introduced — the point where the exit happens is itself one of the three existing boundaries" (§5)

## 0015-session-error-retry-plan
- Date: 2026-09-09 (Status: implemented 2026-09-09; corrections dated 2026-09-09, 2026-09-10 addendum, 2026-09-12 ×2, 2026-09-16 ×2, 2026-09-17; provenance addendum 2026-10-03)
- Trigger: T-062 postmortem (`/workspace/kernel-dm-stripe`) — a Kimi 5-hour-limit 403 (`isRetryable:false`) made the retry loop swap in blank new sessions with no regard for accumulated progress, sidelining the session that did the work; premature `remember()` persisted the last blank error-stub session as the "recoverable session"; the next run reused it, forcing full state rediscovery — strictly worse than not reusing at all; structured fields like `isRetryable` were read and thrown away.
- Rulings:
  - Non-retryable errors (`isRetryable === false`): no "swap in a new session and retry" loop — return `blocked` directly, `chain.id` stays untouched (a session with real content is not sacrificed). (Confirmed decisions)
  - Retryable transient errors: fork an independent copy and retry the same prompt on it (fork source later changed — see the 2026-09-12 correction). (Confirmed decisions)
  - Fork copy retries successfully → "promotion": `chain.id` = the copy's id; the original session need not be explicitly deleted — it sinks naturally. (Confirmed decisions)
  - Fork copy still fails → discard the copy and re-select a source by value for one more try until `RETRIES` exhausted (after the 2026-09-12 correction: a copy that has itself accumulated more context becomes the new preferred source). (Confirmed decisions)
  - `chain.id` empty (the session's first message never succeeded): corrected 2026-09-12 — if the failed session itself has accumulated usage, fork it; only a pure error stub (used=0) falls back to re-seeding from the fork base; only when even the base is absent does it open a blank new session; the criterion for "nothing worth protecting" changes from "whether the chain has a session" to "whether the failed session has content". (Confirmed decisions, 2026-09-12 correction)
  - `remember()` persist timing: originally moved to "after confirming this round is not a retryable session error" (point 4) — addendum 2026-09-10: refined by plans/0018 into "write on dispatch + restore the pre-dispatch snapshot on retryable failure". (Confirmed decisions + addendum)
  - `watch()`'s `session.error` handling also extracts `isRetryable` (missing or non-`false` treated retryable — conservative default); a single `false` anywhere means non-retryable (pessimistic reading). (Changes 1)
  - `attempt()`'s blocked return carries `retryable` out. (Changes 2)
  - `runSession()` retry loop: check `retryable === false` first (no fork, no retry); otherwise fork from the chain's session into `chain.pending` without modifying `chain.id`; `chain.id` may land on the failed session only on non-session-error blocks or the success path — the retryable path restores it to the original. (Changes 3)
  - Point 5 backstop: `runTask()`'s cross-process resume decision adds a "last round is not a pure error stub" check (`usage.used === 0 && errorStub`) — belt-and-suspenders against legacy `progress.json` records. (Changes 5)
  - correction (2026-09-09, T-063 postmortem): point 5's criterion falsely killed long sessions — `sessionUsage()` computes `basis` = the first assistant message, walking backward from the last, that actually ran to completion (`tokens.input + tokens.cache.read > 0`); `errorStub` is true only when the whole session has no `basis` and the last row is itself an error. (Post-hoc correction)
  - correction (2026-09-12, preserve the most valuable session): retry source selection in descending order of accumulated context usage — ① the just-failed session itself, ② the chain's original session, ③ the fork base (re-seed), ④ blank new session; three invariants (always fork a copy rather than reuse directly; the copy inherits the source's `used`; the `seedForkSession` "cold-start once usage reaches cap/2" guard does not apply to retries). (2026-09-12 correction)
  - correction (2026-09-12, two — ladder and adjudication): retry count/waits `OPENCODE_AUTO_RETRY_WAITS` default `0,1,2,4,8` (first retry immediate, then minute-scale backoff); ladder exhausted → manual adjudication `OPENCODE_AUTO_RETRY_ASK` default 30 min; human "continue" restarts the ladder (no round cap); human "exit" blocks immediately; timeout/off-topic/stdin-closed → fallback = switch to the next candidate model, block only when candidates exhausted. (2026-09-12 correction two)
  - correction (2026-09-16, three — wait-and-probe loop): manual adjudication and blocked exit replaced by the `awaitRecovery` wait-and-probe loop — non-retryable errors, ladder exhaustion, and fallback-candidate exhaustion all wait indefinitely at `OPENCODE_AUTO_RECOVERY_WAIT` (default 30 min), probing each round with a brand-new temporary clean session; on recovery fork the interrupted session (same most-valuable-session criterion) and resend with a one-time recovery note; prime directive: a session failure never exits the program; `askRetry`/`OPENCODE_AUTO_RETRY_ASK` retired; failure surface extended to creation/dispatch failures and SDK exceptions (in-session blocking questions and permission denials still return blocked — they need a human reply, not failures). (2026-09-16 correction three)

## 0016-stuck-loop-design
- Date: 2026-09-09 (Status: "implemented (2026-09-09)")
- Trigger: Weaker models show a stable failure class — doing the same action over and over and failing each time (same "String not found" edit, micro-tuned retries with verbatim-identical errors, re-reading the same file with identical output) — that none of the existing mechanisms covers: the idle watchdog handles no output, the context-handover steer handles usage-limit overrun, silent-block detection rules only after the session ends.
- Rulings:
  - Two criteria scoped to the session, observing the terminal state of every tool call: `error` same-error repeat (tool name + error text, parameters excluded, threshold 3) and `repeat` same-args-same-result repeat (tool name + parameters + output text, threshold 4). (§2)
  - Signature rules: the error criterion ignores parameters; the same-args-same-result criterion requires exact sameness of parameters and output; any change in the result counts as progress; consecutiveness not required; signature normalization = whitespace folding + lowercasing; parameters serialized sorted by key, long texts compressed into short hash keys. (§2)
  - Thresholds and caps are exported constants of `src/stuck.ts` (`STUCK_ERROR_REPEAT`/`STUCK_SAME_REPEAT`/`STUCK_MAX_HINTS`), injectable for unit tests. (§2)
  - Hints steered into the session via `session.promptAsync` (entering at the next provider-turn boundary); the `stuck-hint.md` copy escalates level by level (1 evidence + re-check premises + switch approach; 2 write out goal/tried-and-failed/next before acting; 3 stop retrying, mark `AUTO-FIXME: <原因与计划>`, report progress, end the session). (§3)
  - At most 3 hints per session; on a hit that signature's count resets to zero (no pestering every call once triggered); after the cap, detection continues but stays silent. (§3)
  - Hint only, no shutdown: detection does not abort the session, change verdicts, or write any state file; a failed steer delivery is only logged, not treated as a block. (§4)
  - Switch `OPENCODE_AUTO_STUCK` (on|off, default on), registered in the switches registry, not persisted; dryrun preflight sessions never checked regardless of the switch (repeated errors are their normal shape). (§5)
  - Relations: independent of the context-handover steer (each counts on its own); orthogonal to `--test-by-driver`; complementary to the `--handover-test` cross-session reminder (this one is in-session, action-level). (§6)
- Supersession: none seen.
- Principle candidates (verbatim):
  - "The driver is the only party that can see from outside that "you have already done this three times", so the driver detects it and proactively hints." (§1)
  - "**The error criterion ignores parameters**: micro-tuned parameters still hitting the same pit is the most typical shape of a weak model, and a changed parameter must not be treated as a new attempt." (§2)
  - "**The same-args-same-result criterion requires exact sameness**: parameters and output both verbatim identical, so the call brought no new information." (§2)
  - "**Any change in the result counts as progress**: a different error or different output is not counted, without guessing which changes qualify as "real progress" (the cost of guessing wrong is misjudgment)." (§2)
  - "**Consecutiveness is not required**: alternating retries like `A,B,A,B,A` are equally stuck loops, recognizable simply by accumulating by signature; signature normalization (whitespace folding + lowercasing) absorbs formatting differences." (§2)
  - "Detection **does not abort the session, change verdicts, or write any state file**. However sound, the criteria can still misjudge (some tasks genuinely require repeatedly running the same command to wait for external state to change), and the cost of a shutdown far exceeds one superfluous hint" (§4)
  - "the level-3 hint hands the "wrap-up" decision back to the model, which writes out AUTO-FIXME and progress and then naturally ends the session, the existing pipeline (acceptance/review/fallback to pending) taking over." (§4)

## 0019-stats-timing-design
- Date: 2026-09-11 (Status: "implemented (2026-09-11, P1..P7 all landed")

- Rulings:
