## 0. The diagnosis (measured 2026-10-21, not asserted)

The corpus: **108 numbered documents, 26,804 lines, ~3.07 MB**, numbering 0001–0109 continuous except 0028 (deliberately deleted with its content absorbed — commit `aca18dab1`; residual references survive in `plans/0035-protocol-string-registry.md`). There is **no index, manifest, or README of any kind** in `plans/`. Formats evolved through three eras (early "Confirmed Decisions" numbered lists → middle `§`-sections with P-n person rulings → recent `## Dn` decision sections under a `## The ruling` narrative), so extraction cannot assume one grammar. Cross-referencing is heavy — 63 files cite other plans by path, 24 carry supersession language — but supersession is recorded inconsistently: a `Status:` line, a strikethrough, a dated correction note, or nothing.

The proof the layer is missing is one rule's lineage. P1 — *the shipped artifact stands alone* — was stated exactly once, in 0036 §4.1 (2026-09-21: "the target code has to stand alone once the process documents are gone"), then adopted by a root plan (`plans/AUTO_NEXT_REFACTOR_PLAN.md`) that **no longer exists on disk or in git history**, reconstructable only through 0045 line 15's citation of it. It was then re-derived **five times in three days**: 0103 first ruling (scope — destination only), 0103's in-file addendum (timing — record during rounds, enforce at release), 0106 (remedy — restate, never delete the record), 0108 (structural definition — deliverable = what a nested repo's git manages), 0103's addendum two (unification — release the single enforcement moment), 0109 (presentation — counts, not lists). Both documented drift points — 0045's "working tree as deliverable" reading and 0103's process-path carve-out — were **codifications narrower than the ruling they recorded**, each corrected only when a third field project tripped on it. That is the accretion pattern: the principle exists; nothing holds it; every incident re-derives a clause and writes it as a new rule.

Principle-bearing content today lives in four places, all entangled with mechanism detail: AGENTS.md's Core invariants (7 bolded, mixed general and piecemeal), `docs/structure.md` responsibility cells (rulings and dates embedded per row), src file headers (the declared "first carrier of design", heavily loaded with plans pointers), and the plans themselves. AGENTS.md's Navigation section alone carries 65 bullet lines totaling ~69k characters of ruling history. Meanwhile AGENTS.md already declares that `docs/` holds "durable overall architecture, **design principles**, and code-location indexes" — the principles layer is **promised by the documentation system and does not exist**.

## 1. The goal

Rationale lookup becomes **principle → mechanism → code**, never a search across the corpus. A question raised at a boundary is answered by derivation from the principle set; a ruling that cannot be derived is recognized as either a principle amendment or a mistake — never silently absorbed as "a new rule". The constitution is small enough to hold, general enough to generate the rule families, and honest about its tensions.

## D1 — `docs/principles.md`: the constitution layer

The durable design constitution, in `docs/` beside structure/shell-contract/glossary. Principle ids **continue the established P-numbering**: today's P1 ("process documents are not design dependencies" — the shipped artifact stands alone) keeps its name and identity; the distillation adds P2..PN. Target ≤ ~20 — the count is an output of the combing, never a quota; if the corpus generates thirty, the synthesis reports thirty and says why.

Each principle carries five parts:

- **Statement** — one general sentence.
- **Rationale** — why it exists, from what failure class.
- **Derivations** — the rule families it generates today, each with its code home and the plans pointer of the family's first ruling. The derivations section is what makes the principle *falsifiable*: a rule that claims the principle must appear here or the claim is wrong.
- **Provenance** — the first ruling that stated it and the incident that provoked it.
- **Known tensions** — where it bends and which principle it trades against (e.g. record-don't-block trades against fail-closed; the manual suite's stricter line trades P1 against "no release gate stands behind an agent-driven run").

The worked example that proves the format before any combing runs — P1's five clause-derivations: scope (0103 first ruling), timing (0103 second ruling), remedy (0106), structural definition (0108), presentation (0109). One principle sentence generates the whole family; the six documents are its case law, not six rules.

## D2 — `plans/INDEX.md`: the corpus manifest

The one **maintained** file in `plans/` — the corpus's front door. (The "retired once obsolete, never maintained" convention governs the numbered historical documents themselves, not the map over them.) One row per document:

`NNNN-slug | what it ruled (one line) | status | principle assignment | code homes`

Status is exactly one of: **active authority** (its rulings still govern), **superseded-by NNNN** (a later document re-ruled it, pointer given), **historical-only** (retirement banner / stage-assist record). Principle assignment names the P-ids its rulings derive from — this is the rule→principle half of the audit (D6) made durable. Two anomalies get their own rows: 0028's deliberate deletion (with the commit and the residual references), and the absent root plan `AUTO_NEXT_REFACTOR_PLAN.md` (cited by 0045 line 15, present in neither disk nor git history — the lineage gap that motivates the index). **Originals stay byte-untouched** (the maintainer's ruling, D8).

## D5 — The derivation discipline (how to rule, going forward)

`docs/principles.md` carries a closing **"How to rule"** section, and every future `plans/NNNN` document's decision blocks state their derivation:

- `Derives: P-NN` — with the one clause showing *how* the ruling follows;
- `Amends: P-NN` — when the ruling genuinely extends the constitution, with the principle restated and provenance carried forward.

A ruling that matches no principle is a red flag to resolve **before** landing: either the constitution is incomplete (fix the set, in the same change) or the ruling is drift (fix the ruling). Answering a boundary question starts from principles.md, not from a corpus search. This discipline is the actual fix for the trigger incident — it converts "claimed it was a new rule" from an invisible error into a named one.

## D6 — The audit contract: findings only (maintainer's ruling 1, 2026-10-21)

Two directions, both recorded in this document's execution record as follow-up work items — **each fix gets its own later ruling; no code change of any kind lands with this initiative, comments included**:

- **Rules → principles**: every surviving (non-superseded) rule family from the combing is assigned to its principle(s). Gaps are findings of two kinds: a *missing principle* (propose the addition) or an *orphan rule* (drift finding — a rule that generates from nothing the corpus can state).
- **Principles → code**: each principle's enforcement points located in src (the headers already carry plans pointers; the mechanisms are findable from them), checked for consistency with the principle's statement. Divergences recorded as findings only.

## D7 — The method: combing, synthesis, one checkpoint (maintainer's ruling 3, 2026-10-21)

- **Combing** by parallel batch agents over the 108 documents in line-balanced batches (~10; the four 800+-line documents weighed). Per document, extract: number/title/date (Status lines first, git add-dates as fallback — mtimes are uniform, the 2026-10-03/04 bulk translation), trigger incident, rulings one line each, supersession signals, **principle-candidate sentences** (the general statements later rulings reuse — the corpus's own phrasings, collected verbatim), code touchpoints. The same pass combs the other three carriers (AGENTS.md invariants, structure.md rows, a sample of src headers) so the synthesis sees all four. Extractions are written to disk under `plans/.0110-work/` — one self-headed file per batch (range, date) — so later stages survive session loss; the work directory is transient, untracked, and removed at stage 8 (D10; renumbered from 7 by the redirect, 2026-10-21).
- **Synthesis** clusters the candidates into the draft principle set in the D1 format.
- **One checkpoint**: the draft set is presented to the maintainer before anything is re-keyed — *their rulings must be faithfully generalized, not re-invented by the agent*. The draft is held outside `docs/` until approved. After approval the remaining stages run to completion.

## D10 — The resume protocol: state lives on disk, never in the session

Execution may span sessions and be broken anywhere. The protocol transposes the driver's own recovery philosophy onto this initiative — re-derivation from durable evidence, completion never judged by self-report:

- **The journal.** An `## Execution record` section appended to this document: one dated line per stage boundary naming the stage, the artifact written, and any ruling taken; the Status line above is updated as stages complete. This document plus the work directory are the entire resume state.
- **The work directory.** `plans/.0110-work/` holds every in-flight artifact — `batch-NN.md` (one per combing batch), `principles-draft.md`, `positioning-and-tiers.md` (stage 2b), `principle-index.md` (the pre-staged canonical index, D17), `assign-batch-NN.md` and `draft-*.md` (child-session outputs, D17), `assignments.md`, `findings.md` — each written whole by its owning step, untracked, removed at stage 8. **A file's presence and well-formedness is the only completion signal for the step that writes it**; the journal is a hint, never proof. An absent or unparseable file means the step re-runs — safe by construction, because combing is pure extraction over read-only inputs and every step overwrites only its own file.
- **The person gate.** The stage-2 checkpoint may not be resumed past: proceeding requires the journal's approval line — the date plus the maintainer's decisions verbatim, draft edits included. A draft present without an approval line means *awaiting review*, never *approved*; an approved draft is never re-presented.
- **Append-only findings.** `findings.md` rows are numbered and never dropped by a re-run; a re-run that no longer observes a recorded finding notes the disagreement beside it rather than deleting it.
- **Person edits win.** If the maintainer has hand-edited an in-flight artifact, the edit is authoritative and the run adapts to it (0100's person-edited rule transposed); no step overwrites it to "complete" itself.
- **Stage-6 boundaries** (the restructure; renumbered from 5 by the redirect). The re-key lands one whole file at a time in the fixed order — `docs/principles.md` → `docs/releases.md` → `plans/INDEX.md` → `docs/glossary.md` → `docs/structure.md` → AGENTS.md (order extended by D15, 2026-10-21) — with a journal line per file. A resume re-derives progress from the journal plus `git diff`, never re-keys a file from stale content, and the stage-8 originals-untouched check over `plans/NNNN-*` remains the outer guard.

## D11 — Positioning: the anchor above the principles

`docs/principles.md` opens with the positioning statement — what the tool is (a person-governed driver for long-range software work), for whom, the exchange (person supplies intent and consequential decisions at brackets; the driver supplies the bounded mechanical span between them), the four guarantees (verifiable completion, the standalone deliverable, the person's decisions never silently consumed, the record outlives the tool), the fences (not a content judge, not unattended automation, not a platform, not project-specific), and the substrate (git and plain files; agents replaceable). Every clause corpus-cited. The statement is §0 of the work draft `plans/.0110-work/positioning-and-tiers.md`; the maintainer rules on it at checkpoint 2b. The positioning is the tier test's ground: **a principle is constitutional only if its removal breaks a clause of this statement.**

## D12 — The tiered rule space (extends D1's format)

The constitution holds two principle tiers plus two registers; concrete requirements leave the constitution and live with their mechanisms:

- **Tier I — constitutional principles**: identity-level; removal breaks a positioning pillar, fence, or contract. Versioned `Amends:` only (D15). Proposed: six (the four pillars P1/P2/P3/P18, the fence P7, the contract P4).
- **Tier II — operating principles**: standing policies; removal degrades how the tool runs without changing what it is. Each carries **choice / chosen default / revisit trigger** beside the draft's five parts — the maintainer's "optional trade-offs" made structural. Proposed: twelve (ownership P5+P11 merged, P6, P8, P10, P12, P13, P14, P15, P16-genericity, P17, P19, P20).
- **Concrete requirements**: mechanical, testable, right-or-wrong by inspection (formats, grammars, thresholds, security mechanics) — they live with their code (headers, `docs/structure.md`, INDEX), never in the constitution. Proposed demotions: P9 → the presentation convention; P16's references/secrets half → the security requirement family. P-ids are never reused (P13's own discipline): P9/P11 tombstone in the numbering note, P16 restated as genericity alone.
- **The trade-off register**: tension → choice → revisit trigger — the open decisions. **The risk register**: conflict/deviation risk → mitigation → where it last showed — the watched items (deferred-enforcement drift, channel divergence, floor-masks-defect, constitution creep, person-gate throughput, vocabulary freeze vs cleanup, corpus growth).

The full disposition table (all twenty, each with its one-line tier-test reason) is §3 of the work draft. The draft's five questions are dispositioned there: merges resolved by tier (P16 splits; P5+P11 merge proposed), the count question dissolved into the tier question, P20's unification confirmed as Tier II, P7 ranked Tier I.

## D13 — Requirements governance (extends D5's discipline)

A requirement enters only through a `plans/NNNN` ruling stating `Derives:`/`Amends:` **plus the tier it touches**, and a requirement-tier ruling names its code home and test home in the same change. The evidence rule (P19) governs admission: measured field evidence or a named incident, citations required. The traceability chain — positioning → Tier I → Tier II → requirement → code home → test home — is audited in both directions each release (D6's audits become per-release). Growth constraints: the constitution bounded by the tier test, never a quota; requirements never migrate upward without an `Amends:` ruling; orphans are audit findings. Between releases findings accumulate; **a release event is the only moment the constitution or a Tier II default changes.**

## D14 — Release-version organization

There is no version practice today (no tags, `version: 0.0.0`, the plans corpus the only history); the framework starts from zero and stays documentation-layer in this initiative (D8's zero-code rule holds; tooling is follow-up findings):

- **The version spine** (semver as the design-evolution axis): major = a Tier I amendment or a breaking contract change; minor = a new opt-in mechanism (floor-preserving, P10) or a Tier II default change; patch = ruled defect fixes (defects exempt from the floor, 0057 §11.1). Pre-1.0, minor may carry breaking changes, said so in words; discipline tightens at 1.0.
- **`docs/releases.md`** — the maintained release record: one section per release (version, date, principles deltas with P-ids and tiers, mechanisms added/retired with plans pointers, tombstones, the D9 falsification-replay confirmation, findings disposition). Git history stays the code audit trail (P18); this is the *design* changelog. **D8's new-file list is extended by this ruling.**
- **INDEX gains a release column**; the corpus 0001–0109 baselines as `pre` (no retroactive versioning; originals untouched).
- **Amendment lifecycle**: `Amends:` rulings name their release; principles.md stamps "current as of release vX.Y"; the falsification replay runs per release.
- **Deprecation lifecycle**: tombstone → one release of visible warning (P8) → removal in a named later release — P13's additive-only discipline on the version axis.
- **Cadence**: a release is cut when a ruled program completes; the maintainer cuts it. The first release records this initiative's landing.

## D17 — The continuation method: child sessions (maintainer's ruling, 2026-10-21)

The maintainer's direction, verbatim: *"I prepare to continue the plan in a new session, and you'd better use child sessions to make the context of the main session keeps clean."* Stages 4–8 execute through that method, in a fresh session that resumes from this document alone:

- **The main session orchestrates; children read.** The main session reads only the control surfaces — this document (Status + journal tail), `plans/.0110-work/principle-index.md` (the pre-staged canonical index, below) — and writes only the plan journal, the stage merges (`assignments.md`, `findings.md`), the six re-key targets of stage 6, and the commit boundaries. - **Stage 4** fans out children over the batch files (~4 children, ~3 batches each); each child receives the principle index verbatim plus its batch file paths, and writes its own `plans/.0110-work/assign-batch-NN.md` — one row per document (`NNNN-slug | what it ruled (one line) | status | principle ids | code homes`) plus any orphan-rule or missing-principle flags observed. The main session merges the rows into `assignments.md`; INDEX's body comes from the same merge at stage 6.
- **Stage 5** dispatches a child (or a plain script, where it suffices) over the principle-index ↔ src homes check — existence of each named file, key symbols present; divergences returned as numbered findings, appended by the main session.
- **Stage 6** dispatches one drafting child per re-key target (given the target file, the principle index, and the file's owning decision from D1–D4/D12/D14); each child writes its draft under `plans/.0110-work/draft-<name>.md`. The main session lands each file whole in D10's order (filesystem copy), reviews the constitution (`docs/principles.md`) in full before landing it, and spot-checks the rest. **Children never write `docs/`, `plans/INDEX.md` or AGENTS.md directly** — the main session is their single writer (P5's discipline applied to the initiative itself).
- **Stage 7** runs the falsification replay in a child that receives `docs/principles.md` alone (plans closed) and returns its answers; the main session compares them against the recorded rulings.
- **Stage 8** the main session runs directly — typecheck, the full suite, the originals-untouched check, cleanup — their outputs are small.
- **Resume**: a child's output file present and well-formed is its completion signal (D10's rule extended to `assign-batch-NN.md` and `draft-*.md`); a lost child is re-dispatched, never re-read. The pre-staged `principle-index.md` is the verbatim prompt input for every stage-4+ child, so no child ever needs the session's history.
