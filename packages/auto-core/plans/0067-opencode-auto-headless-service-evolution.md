## 1. Conclusions (TL;DR)

The direction holds, and the codebase has already been consciously evolving toward it; the migration cost is much lower than expected. The original five-component split (headless execution core / dynamic-config tool suite / REST API module / pure Web client / simple command-line console) is broadly correct but needs two corrections:

1. **The "headless execution core" already exists**: it is `auto-core` itself. Do not fork or rewrite it; just add a shell package in server form. The core never knows HTTP (core/shell contract: core does not know shells).
2. **"Dynamic config" must be reinterpreted**. The config model of this program is deliberately "anti-dynamic" (init locks it in → amend revises it → frozen at runtime; a constitutional key appearing at runtime means exit 1). The correct meaning is **API-reachable** (API-driven pre-run config), not **mutable mid-run**. Breaking the config constitution is the only path by which this migration could ruin the whole design.

## 2. Why the Direction Holds (current-state inventory)

### Servicization foundations already in place

| # | Fact | Evidence |
|---|---|---|
| 1 | The whole runtime is one library function | `src/loop.ts:33` `runAll(directory, opts: RunAllOpts): Promise<number>`; `planPrelude` / `closeUnit` / `task-add` / `renderStatus(dir)` are likewise directly callable. The CLI shell (`packages/auto`) is only ~1600 lines of argument parsing and printing |
| 2 | The CLI form belongs to the shell, and a server legitimately is "another shell" | `docs/shell-contract.md` §A decision rules; the injection points `setShellProfile` / `registerTemplate` / `registerAgentAdapter` all exist already |
| 3 | Human interaction is already transport-agnostic at the key points | The `Interactive` sideband accepts injected `io: { input, output }` streams (`src/interactive.ts:34`, defaulting to stdin/stdout); the control plane is in-process service calls: `Control.requestExit()` (`src/exit.ts:37`), `Router.requestFailback(order)`. `/exit` and `/failback` are essentially methods waiting to be invoked over WebSocket |
| 4 | Observability is disk-based and naturally multi-process safe | `renderStatus(dir)` purely reads unit files + `.auto/units.json` + the phase index; `status` never takes a lock and is explicitly designed to coexist with a running process; every run writes a complete synchronous audit log `.auto/logs/run-*.log` |
| 5 | One driver per directory is already enforced | `.auto/run.lock` (pid+host JSON, stale-pid detection, `src/lock.ts`) → one daemon supervising N workers over N directories is safe today |
| 6 | Crash and kill are isomorphic; workers can be cattle, not pets | `src/exit.ts` header comment: with progress persisted, the next run resumes "precisely"; `/exit` produces, at any safe boundary, a state fully isomorphic to a real kill. The supervisor may kill/restart workers at will |
| 7 | There is already a REST+SSE precedent at the layer below | The opencode adapter itself spawns/takes over `opencode serve` and consumes SSE (`src/agent/opencode/`); this monorepo already has the same architecture (`packages/server`, `packages/web`, `packages/console`) |

### Locations still terminal-bound (an honest list)

| Location | Current state | Migration handling |
|---|---|---|
| `loop.ts:92-96` SIGINT → exit 130, `process.exit` | Assumes it owns the whole process | The run executes in a subprocess; isolation comes for free |
| `lock.ts:61` process exit hook releases the lock | Same as above | Same as above |
| The readline in `confirm.ts` / `session-api.ts askHuman` / `loop-progress.ts waitBetween | Connects directly to stdin (some already support injected io) | Those serving one-shot config commands map to POST; in-session Q&A goes through `Interactive` injection |
| `log.ts` is a module-level singleton that console.logs human-readable prose | No event bus | The only core mechanism that genuinely must be added (see below) |

### Three real gaps

1. **No structured event bus**. The only real-time signals are terminal text + audit files, and log lines are prose for humans, not a protocol; the Web side must not scrape them. `RunServices` needs a small event-emitting service added (an exactly matching precedent: that is how 0061 turned `control` and `router` into services), feeding the log file and the SSE subscribers at the same time; events are structured (unit transitions, session start/end, question, usage, error), with absolutely no scraping of English text.
2. **Blocking Q&A flow**. The `humanQuestions` of the `plan` session waits for a human with no timeout; the Web side must handle disconnect/reconnect, so the server needs a **pending-question queue + persistable delivery** rather than a single WS message. The integration point is exactly `Interactive.question()`.
3. **Process topology**. `runAll` must execute in a subprocess, not inside the API process: SIGINT/exit-hook assume process ownership, and subprocess isolation brings the kill/recovery story for free.

## 3. Corrected Target Component Split

1. **Headless execution core = `auto-core` evolving in place**. Only add: the event-bus service; (optionally) make the io of the last few readline spots injectable too. The core never imports HTTP.
2. **Dynamic config = respect the constitution**. init/amend/fix/reset exposed via API (pre-run); per-run overrides go only through the existing env-switch layer (`OPENCODE_AUTO_*` → the per-run options of the API); mid-run changes go only through the existing control plane (`/exit`, `/failback`, `close`, `task-add`). "Dynamic" = API-reachable, not mutable mid-run.
3. **REST/SSE module = a new shell package** (working name `packages/auto-server`). The resource surface derives directly from the command list:
   - projects (target directories, registered via the daemon-level allowlist)
   - runs: POST returns a run id immediately; run lock conflicts map to 409/423; exit 0/1/2/130 maps mechanically to HTTP status
   - config ops（init/amend/fix/reset）、units（close / task-add）、plan（input / append / force-close）、models
   - SSE: logs, events, status; WS: interactive + the question queue
4. **Pure Web client**: consumes the status tree, the event streams, and the question queue. A thin layer on top of 3.
5. **Simple command-line console: `packages/auto` kept as-is**. It remains the reference shell, the escape hatch when the daemon is unavailable, and the regression baseline.

### Process topology (proposed)

```
daemon (supervisor, packages/auto-server)
 ├─ REST API + SSE/WS endpoints
 ├─ run registry: runs/{id} → (dir, pid, state)
 └─ one subprocess worker per run
     └─ runAll(dir, opts)   ← .auto/run.lock guarantees one instance per directory
                                ↑ disk read model: .auto/*.json + .auto/logs/*.log + git
```

## 5. Risks and Constraints That Must Hold

The credibility of this tool comes precisely from those "inconvenient" invariants, and the biggest risk of going Web is bypassing them for convenience:

- **The driver has exclusive rights to write state**: API/Web must never write directly to `.auto/`, `todo.md`/`done.md`, or index ticks; every change goes through library functions such as `closeUnit` / `task-add` / `runAll`.
- **Unified commit is the completion condition**: "done" on the Web must be judged by the commit (③ commit / ④ dirty); never trust agent self-reports.
- **Config constitution**: do not introduce mid-run config changes just because the Web is convenient.
- **One run per directory**: horizontal scaling happens only along the directory dimension, never concurrently on the same directory.
- **Amplified trust boundary**: the `.opencode/auto/` overlay gets injected verbatim into the prompt (equivalent to executing the instructions of that repository); a one-click Web trigger for runs on arbitrary directories amplifies this risk → the daemon must maintain a target-directory allowlist, and the API needs token auth (this tool spends real money on tokens and writes to git).

Three findings span several units and are stated once each:

- **The fake-agent question-capability limitation (the workaround pattern).** The fake `claude` fixture cannot raise an agent question: the claude adapter's own capability table turns them off (`question: false`, `src/agent/claude/client.ts:38` — the agent contract disallows AskUserQuestion), and no core change may alter that. Every e2e that needed an agent question (P3c's plan session, P4b's write-surface centerpiece, the close-out e2e's plan step) therefore pinned the composed chain in two halves over the **same transport, queue and `answer` scope** a real planning question rides: the planning run spawned with its interactive channel live (the `session` frame observed over the worker bridge — the channel a plan question takes), and a real hard-wait question — the exact `askHuman`-with-`minutes: undefined` shape of `src/session-api.ts:364-397` — asked through the run's own between-tasks pause, answered across a daemon restart through the pending queue. The chain is covered end to end modulo the asker; the core's mapping of answered/degraded asks into the session is pinned core-side (`test/turn-questions.test.ts`).
- **The macOS git-identity e2e caveat.** `packages/auto`'s e2e case "init prerequisite: a git repository whose identity cannot commit is refused" fails on macOS hosts: the fixture shields `HOME`/`XDG_CONFIG_HOME` and sets `GIT_CONFIG_NOSYSTEM=1`, but Apple git still auto-detects a full `GIT_COMMITTER_IDENT` from the OS account, so the core's `commitIdentityProblem` rightly finds an identity and init proceeds with exit 0 instead of the expected refusal 1. Pre-existing and environmental: A/B-verified against the untouched tree (T-086) and reproduced with git alone (T-091); it failed in the P1..P3a units' verification runs and passed again from T-094's on. Durable consequence adopted in the new fixtures: `auto-server`'s fixture project sets a repo-local git identity instead of leaning on the ambient account (T-087).
- **Host discipline.** Run the packages' suites one at a time on this host class — concurrent full-suite runs flake on transport/timing under load (T-091 documented the class; T-092's transport flakes were it). Separately, `packages/auto-server/test/status-events.test.ts`'s backpressure case is timing-flaky under full-suite load on a clean tree (T-096 A/B'd it against a pre-task `git archive` extract: 2 of 6 runs fail) — observed, not introduced, left unchanged.

**P1b / T-087 — the worker entry: one child process per run, 2026-10-01.**
- Landed: `src/worker.ts` — a process entry (never an in-process library; the daemon spawns `opencode-auto-server worker '<json>'` and never imports it) that parses, validates, runs exactly one `runAll` and exits with its own code. **P1d / T-089 — the REST lifecycle surface: config ops, units, models, the plan boundary, 2026-10-01.**
- Landed: `src/ops.ts` (`OP_DEFINITIONS`) and the `/projects/<p>/<op>` routing: init/amend/fix/reset (`config`), close/task-add/plan (`control`), models (`read`). **Operations run in the daemon process as library calls into the core** — an operation is a synchronous request/response with no session and no exit vocabulary of its own, so none of the worker's `runAll`-invariants apply (SIGINT ownership, per-run env, the log fd, the memoizing switch layer). Every state change reaches disk through the core's own writers; the write boundary is pinned as a standing test (nothing in `src/` writes a target's `.auto/`, `docs/` unit state or an index file). Plan is the P1 boundary: only `planPrelude`'s no-agent outcomes are served; the `{ type: "loop" }` route and the planning-input fields refuse 501 (a planning session runs `humanQuestions` — a wait with no timeout — and a headless worker's closed stdin only degrades it to blocked). Daemon-side concurrency guards beside the run lock: a per-directory in-flight op slot and the live-registry-run check for write ops (the lock is re-entrant per process — it arbitrates processes, not requests), mirrored on `POST /runs`.
- Durable: the confirmation is never skipped, only answered — the `confirm` field routes through the core's io-injectable confirm gate via injected io (the gate's own normalization decides; the CLI's `-f` "skip the prompt" becomes "answer the prompt with the caller's y"), and an unanswered destructive request answers **428 carrying the exact question** (rejected: a silent 200-cancelled default — a stateless API whose silent default was cancelled would let scripts believe they had written); `confirm` and `cleanTree` are two separate request fields, each flipping only its own gate (all four combinations pinned); task-add routes through `planPrelude`'s `--new-task` row (rejected: re-implementing the guard chain beside the core's — the constitution-erosion risk); `fix --dryrun`'s findings answer 409 `code: 1` (the CLI's scripted-gate exit semantics preserved); request-shape errors answer before any target read; the request speaks the config-file (camelCase) vocabulary, kebab spellings refused; models describes the daemon's own filtered run environment (per-run overrides ride run requests, not the daemon env); a second reset meets the clean-tree gate (reset never commits — the diff is left for review).

**P1e / T-090 — disk observability: the SSE tails and the polled read model, 2026-10-01.**
- Landed: `src/observe.ts` — three read-only routes beside a live run, no lock taken, `.auto/` stays driver-exclusive: `GET …/status` (the polled read model: the core's `renderStatus(dir)` lines imported and called as-is; completion verdicts — a unit is done exactly when its `done.md` exists, commit-is-completion, agent self-reports never trusted; per-worktree git cleanliness over the core's `repoRoots`, nested repositories included; the lock holder line) and the two SSE tails `GET …/log` / `GET …/events` (whole-line framing; the log's prose lines delivered verbatim and never parsed; the typed engine journal's lines delivered as structured payloads; both rotation rules — the log rotates by new name (the tail re-seeks to the new file's start, `reason: "rotated"`), the journal by truncation (re-seek to 0); ticks serialized by a re-entrancy guard — two in-flight ticks deliver the same offset range twice).
- **Defect found and fixed: the git-status poller taking `.git/index.lock`.** A plain `git status` opportunistically refreshes the index; under the observer's ~100–150 ms polling it collided with the observed run's own `git add` — the run's unified commit failed ("Unable to create .git/index.lock: File exists") and the run ended **blocked**: the observer blocked the run it was watching, roughly one suite run in five. Fix: the poller's status read passes `--no-optional-locks` (`packages/auto-server/src/observe.ts`, `worktreeVerdict`) — git's own flag for background readers; the core's own status reads need no such flag (they run inside the run's process, sequential with its writes). This is the one genuine hazard this plan's "git status reading is trivially safe" assumption missed.
- Durable: the newest run log is discovered by listing and name-sorting the stamp-bearing names, never by mtime (same-second runs share one name — the core appends — and mtime is same-second ambiguous); `.auto` state files are read defensively (`absent`/`torn`/`ok` — a torn file is reported under `unparsable`, served 200, never an error: "retry next tick"); the tails attach at the current run's file beginning, not its end (the newest file IS the current run's — a connecting client sees the whole run it came to watch; no `Last-Event-ID` in P1: the poll model is the durable view); the per-worktree porcelain is re-implemented in the shell, not hoisted (the core's `statusEntries` is private and `changedFiles` flattens worktrees; the discovery and path conversion come from the core's exported pieces so the traversal cannot drift — zero core change).
- Pointers: `packages/auto-server/src/observe.ts`, `test/observe.test.ts`, `docs/daemon.md` (the P1e section).

**P2a / T-091 — the driver-status event table, 2026-10-01.**
- Landed: `src/run-status-schema.ts` — the frozen, additive-only `RunStatusEvent` vocabulary (12 event types: `run-start`, `run-end`, `unit-transition`, `task-start`, `task-end`, `subtask-start`, `subtask-end`, `question-raised`, `question-answered`, `usage-rollup`, `failure`, `exit-request`) plus its declaration tables; the additive-only ratchet (a planted rename or removal fails) and compile-time keying in `test/run-status-schema.test.ts`. The module imports nothing, reads no file, merges nothing, judges nothing — no emission, no subscribers, no server work; every shared shape (unit levels, statuses, outcomes, error classes, usage figures, exit boundaries) is restated structurally with its home named beside it, the joins pinned by two-way `Exact` assertions so the restatements cannot drift.
