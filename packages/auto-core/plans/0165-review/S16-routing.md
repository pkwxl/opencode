**S16-01 (S2).** (1) A two-key ring. Key A hits its quota, the ring rotates to B, and the managed server restarts on B (spawn config `apiKey: {env:B}`). (2) The person swaps or tops up key A and types `/failback`. The next task boundary consumes it: marks cleared, position 0, and the line "key rings rewound to their first key". (3) Nothing restarts the server. The next session's walk finds no marks and does nothing, so every dispatch still runs on B. (4) B's quota runs out with a stated 5 h reset. The rotation reads `from = currentKey = A`, marks A down to B's 5 h reset, lands on B, and restarts onto B. (5) The fork fails on B again. The ring refuses because A is wrongly held, so the run leaves the provider or waits 5 h. Meanwhile the healthy, freshly fixed key A is never used. A second `/failback` repeats steps 2–5.

**S16-04 (S2).** (1) An operator registry routes `phase-plan` to their strongest model, and `simple` lists a cheap model first. (2) `transfer` opens an implement phase. The formulation task's todo carries `Decompose: whole`, so the session's chain phase is `whole`, its role `whole`, and its tier the implement type's `simple`. (3) The cheap model writes every task document of the phase. No line says the `phase-plan` route was not used. Preflight even checked that route's coverage as "the planning need".

**S16-05 (S2).** (1) The tier list is [a, b]. Model a fails quota with a stated 5 h reset, giving a `until` mark. The failover moves to b. (2) b fails with an error that states nothing (no reset header; the classifier is absent or over budget), giving a mark with no `until`. Both are now down, so the wait loop starts. (3) recoveryAt withholds the instant because of b's until-less mark, so the loop polls every 30 min. (4) Each round's probe takes the first in-window candidate, a: it clears a's 5 h mark, probes the spent quota, fails, and re-marks a. b is never probed. (5) If b recovered in minutes, the run still waits out a's 5 h. If one probe round errors on its own, a is re-marked with no instant, and the stated reset is lost.

## Leads

No salvaged lead targets S16 (`leads/README.md`: R5-walk-* are S17's, R4-driver-throw-loop S13's). The seam questions the earlier steps handed to S16:

- **S13 — the session-scope clear erasing reset-bearing marks mid-wait:** **refuted.** `clearDownMarks` → `dropScopeCleared` deletes only marks with `until === undefined` (router.ts:436-442), and key marks never take part. A reset-bearing mark survives the probe's new-session clear (attempt.ts:152-155). What the probe does clear wholesale is the until-less marks. That is scope=session's documented contract ("fails back at every new-session start"), not a loss of a stated reset. The real loss of a stated reset in the wait is S16-05, the probe's own `clearModelDownMark`.
- **S14 — overflow tested first over the turn's merged failure text:** **confirmed by code, folded into S14-02.** `classifySessionError` tests `extra.overflow` before quota over `message + responseBody` (chain.ts:383-385), so overflow followed by insufficient-quota in one turn settles as overflow. The cost is bounded: the next dispatch's turn starts a fresh failure slice and classifies quota, which starts the escalation. It costs one wasted dispatch into the overflowed fork (S13-06's path). S14-02's remedy (classify the event's own error) covers it, so no separate finding.
- **S15 — accountOf at event time vs the rotation instant:** **clean on the serial path.** session.ts:928 reads the account after the session returns and before the escalation commits a rotation. attempt.ts:430 reads at event time, when the position still equals the spawned key. The account is misattributed only (a) after S16-01's rewind divergence (every observation is booked to key 1 while key 2 serves) and (b) under doc lanes, where a sibling's rotation moves the position while this lane's turn still streams on the old key (S17-02's window).
- **S17 — the probe clears every key mark of the provider:** **confirmed** (router.ts:583-586 `clearRingMarks` → `downKeys.get(provider)?.clear()`). It is recorded as S16-05's family and S16-02's impact: the first premature probe is what erases the non-current key's evidence. The fix belongs with S17-01's remedy (clear only the probed key). **The failure rotation's restart under doc lanes** (session.ts:361-382) has the same shape as S17-02's walk restart, with no in-flight check. S17-02's remedy already names it, so no new finding.
