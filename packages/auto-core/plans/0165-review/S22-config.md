### S22-01 failure scenario (S2)

1. Machine A (binary v2) runs `init --intent cleanroom`: pack materialized, stamped, committed — the pack's charter body is v2 wording, headings unchanged from v1.
2. Machine B (binary v1, same checkout): preflight's notice says the materialized files "can fast-forward to the running binary's bundle (sync)"; `fix` reports "the running bundle is newer"; `status` the same.
3. The person runs `sync` as taught: the entry is a fast-forward labelled binary-newer, so formatSyncPlan's only downgrade caveat (`direction === "binary-older"`) does not print; the person confirms.
4. applySync writes v1's bytes over the v2 pack and re-stamps it as v1 — a silent downgrade of committed state, undetected until the v2 binary runs again (and then reported only as another ambiguous body diff).

## Design notes

The area is disciplined: one comparison helper, one rule table, plan-then-apply everywhere, and 0135/0158/0164's exit and byte-honesty rules all verified in code. The weak spot is **crash windows between two durable writes** (S22-02, S22-03, S22-05): every apply is a plain sequential await over committed files with no atomic rename and no idempotent re-derivation for the in-between states — P6's "every step idempotent" holds for the happy path but not for the kill points. Best choice: the provenance three-state design itself (one pure comparator, messages derived from it). Worst choice: the direction ternary asserting "binary-newer" on evidence that cannot name a direction (S22-01) — the one place the detection layer states a fact it does not know, and the person-facing advice compounds it into a downgrade. Fix S22-01 first (person-facing wrong advice), then the two idempotence gaps.
