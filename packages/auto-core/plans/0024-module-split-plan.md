### A.3 Favorable conditions (verified)

- **No module-level mutable state**: `grep '^let |^var ' src/runner.ts src/loop.ts` has no hits; both files are pure-function modules — code can simply be moved, with no "cross-file shared singleton" hazard.
- **Package exports are naturally compatible**: `package.json`'s `exports` is `"./*": "./src/*.ts"`, so new src files need no registration; new modules are automatically consumable via `@opencode-ai/auto-core/<name>` (the AGENTS.md build convention already states this).
- **The call graph is a DAG**: see §D.2; cutting by layer produces no cycles. The only cycle (`watch` → test execution ↔ `runExecSession` → `runSession`) is dissolved by §D.2's "separating test execution from the handover state machine".
- **Tests are already grouped by describe**: the 32 describes in `test/runner.test.ts` and the 28 describes in `test/prompt.test.ts` map essentially one-to-one onto the target modules, so splitting tests is mechanical work.

### A.4 Constraints (verified)

- **The external consumption surface is extremely narrow**: outside the package, only `packages/auto/src/index.ts` takes the two types `PermissionMode` / `SubtaskMode` from `@opencode-ai/auto-core/runner` (**S12 correction**: the migrate shell `packages/auto-migrate/src/tool.ts`, not visible from this branch, additionally takes `requireArtifact` — see §I D12); inside the package, `final.ts` / `implement.ts` / `numbering.ts` / `knowledge.ts` / `config.ts` / `loop.ts` take `requireArtifact` / `afterSession` / `restoreTestHandoffs` / `runOnce` / `runTask` / `Opts` / `UnitStop`.

### D.2 Dependency direction (must stay one-way)

```
opts ─┬─ chain ─┬─ session-api ─┐
      │         │                ├─ watch ─ attempt ─┬─ session ─┬─ artifact ─┬─ review ─┐
      ├─ unit-commit ────────────┤                    │           │            │          │
      │   └─ current             │                    │           │            │          │
      ├─ resume-gate ────────────┘                    │           ├─ exec-session ─────────┤
      └─ testrun ─────────────────────────────────────┘           │                        │
                                                                   └──────── execute ──────┴─ runner
```

**The only cycle and its dissolution**: `watch` must call test execution (`executeTest` / `resolveTestScript` / `runTestScript`), while the handover state machine `runExecSession` must call `runSession`. If "test execution + handover" were stuffed into the same module, you would get the cycle `watch → test module → session → watch`.

The dissolution is exactly D.1 splitting them into two modules:

- `testrun.ts` = **test execution and the file operations on handover documents**; it depends on no session-driving code (uses only `verify.ts` / `prompt.ts` / `docpaths.ts` / `git.ts`) and is a leaf.
- `exec-session.ts` = **the state machine of handover sequencing** (the interrupt-recovery branches and finalization forks of `runExecSession`), sitting above `session`.

So `watch → testrun` (one-way) and `exec-session → session + testrun` (one-way); the cycle disappears. **No future change may make `testrun.ts` import back into `session.ts` / `attempt.ts` / `watch.ts`.**

Other verified directionality facts:

- `watch` calls `afterSession` (the finalized commit of a test handover), hence `watch → unit-commit`; `unit-commit` does not depend back on the session layer.
- `verifyTask` (in `review.ts`) internally calls `runExecSession` and `runSession`, hence `review → exec-session`; `exec-session` does not call review.
- `requireArtifact` calls `runSession`, but nothing inside `session.ts` calls `requireArtifact`, hence `artifact → session` is one-way. `requireArtifact` is consumed by 4 in-package modules (final/implement/numbering/knowledge); giving it a file of its own is precisely so they need not pull in the whole session-driving graph.

## H.1 Construction manual (proven end-to-end in S1; later steps follow this)

The mechanical procedure for each step — a fresh session can simply follow it as written:

1. **Locate**: grep by symbol name; do not use the baseline line numbers in the §D.1 table (they have drifted).
   `grep -n '^export type X\|^function X\|^const X' src/runner.ts`
2. **Extract**: use a python snippet to cut the range out into the new file **verbatim** by line numbers — do not hand-retype; hand-retyping inevitably changes punctuation.
   ```python
   src = open("src/runner.ts").read().split("\n")
   seg = lambda a, b: "\n".join(src[a-1:b])   # 1-indexed inclusive
   ```
   At the top of the new file write 3–4 lines of responsibility notes + `拆分自 src/runner.ts(plans/0024-module-split-plan.md S<n>,纯搬运)` ("split from src/runner.ts (plans/0024-module-split-plan.md S<n>, pure relocation)"), then the imports.
3. **Delete**: the same python snippet deletes the range from runner.ts; **carry one extra line past the range end** to take the blank line after the symbol along too, otherwise consecutive blank lines are left behind.
4. **Wire up**: add `import { … } from "./<新模块>"` (`<新模块>` = `<new-module>`) at the top of runner.ts (keeping the symbols still in use), and append one line to the compatibility re-export block at the end.
5. **`bun typecheck`** — run only this first; it is fast and immediately exposes missed symbols.

7. **`bun test`** — the number must equal the previous step's baseline (**771 pass / 0 fail** after S1); one fewer means a test was lost in the move.
